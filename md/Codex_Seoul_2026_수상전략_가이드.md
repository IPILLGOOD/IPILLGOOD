## 0. 가장 중요한 결론

이 대회는 **코드를 가장 많이 만든 팀**보다 아래 다섯 가지를 한 번에 증명하는 팀에 유리하다.

1. **구체적인 사용자 문제**를 골랐는가
2. 핵심 사용자 흐름이 **실제로, 안정적으로 작동**하는가
3. 주장한 가치가 인터뷰·테스트·피드백 등으로 **검증**됐는가
4. Codex를 단순 코드 생성기가 아니라 계획·구현·검토·오류 복구·검증에 활용했는가
5. 처음 만난 Build/Insight 구성원이 어떤 판단과 역할 분담으로 결과를 만들었는가

수상을 노린다면 기능 수를 늘리기보다 **한 사람의 한 문제를 해결하는 한 개의 완성된 흐름**을 만들고, 그 과정과 근거를 심사위원이 설명 없이도 확인할 수 있게 제출해야 한다.

특히 1차 심사는 별도 발표나 질의응답 없이 제출물만 검토한다. 따라서 저장소 첫 화면과 데모 영상이 이해되지 않으면 좋은 제품도 결선에 진출하기 어렵다.

## 3. 공식 제출물

세 사이트의 내용을 합치면 팀이 준비해야 할 심사 패키지는 다음과 같다.

### 필수에 가까운 제출 구성

1. **실제로 동작하는 MVP**
   - 웹·앱·자동화 도구·데이터 분석 서비스 등
   - 핵심 사용자 흐름을 직접 실행할 수 있어야 함

2. **GitHub 저장소 또는 접속 가능한 서비스 링크**
   - 심사위원이 권한 요청 없이 접근할 수 있어야 함
   - 실행·검토 방법이 저장소 첫 화면에 있어야 함

3. **핵심 사용자 흐름을 보여주는 데모 영상**
   - 문제 → 사용자 행동 → 결과 → 가치가 짧고 명확하게 보여야 함

4. **Codex Build Log**
   - Codex에 맡긴 일
   - 유효했던 프롬프트·지시
   - 실패한 시도와 원인
   - 복구·수정 과정
   - 사람의 주요 판단
   - 테스트와 검증 방식

5. **Value & Viability**
   - 대상 사용자와 문제
   - 기대 가치
   - 핵심 가정
   - 운영 가능성
   - 향후 발전 방향

6. **문제 정의와 검증 근거**
   - 인터뷰, 사용성 테스트, 관찰, 비교 실험, 피드백 등

7. **행사 당일 구현·개선 내용과 역할 분담**
   - 기존 자료를 참고했다면 무엇이 기존이고 무엇을 당일 새로 만들었는지 구분

### 운영 플랫폼에서 실제로 입력하는 항목

[행사 운영·제출 플랫폼](https://hackathon.pseudolab-devfactory.com/events/codex-seoul-students)은 다음을 요구한다.

- 팀 번호: 1–25
- 담당 멘토에게 받은 6자리 제출 코드
- Repository URL
- 마감 전까지 URL 수정 가능

즉, 플랫폼에는 Repository URL 하나를 넣더라도 **저장소가 나머지 제출물로 가는 단일 관문**이어야 한다. 데모 서비스, 데모 영상, Build Log, Value & Viability, 검증 자료를 README 상단에서 모두 찾을 수 있게 연결한다.

### 권장 저장소 구조

```text
README.md                       # 심사위원용 1페이지 요약과 모든 링크
front/                          # 실제 데모 UI와 프론트 검증 스크립트
backend/                        # Firebase, 데이터 모델, AI 연결 경계
md/
  codex-build-log.md          # 위임·프롬프트·실패·복구·판단·검증
  value-and-viability.md      # 사용자·가치·운영 가능성·확장 계획
  validation.md               # 인터뷰·테스트·피드백과 변경 사항
  architecture.md             # 핵심 구조, 데이터·AI 흐름, 한계
design/
  system/                     # 디자인 토큰과 UI 원칙
  screenshots/                # 핵심 화면과 실패 대비 증거
demo/
  demo-video-link.md          # 데모 영상과 백업 링크
```

README 첫 화면에는 최소한 다음이 보여야 한다.

- 한 문장 문제 정의
- 대상 사용자
- 핵심 가치 제안
- 라이브 데모 링크
- 60–90초 권장 데모 영상
- 3단계 실행 방법
- 핵심 기능 3개 이하
- 검증 결과 2–3개
- Codex Build Log 링크
- 팀원별 역할과 당일 기여
- 알려진 한계와 다음 단계

> 영상 길이와 발표 시간은 공식 배점·규정으로 공개되지 않았다. 위 길이는 1차 심사에서 빠르게 이해시키기 위한 실전 권장치다.

## 4. 심사 방식

### 1차 심사

- 팀별 별도 발표·질의응답 없는 **비대면 제출물 심사**
- GitHub 저장소, 배포 서비스, 데모 영상, Codex Build Log, Value & Viability, 프로젝트 소개와 핵심 기능 검토
- 약 5개 팀을 결선 후보로 선정

**의미:** 심사위원이 팀에게 물어보지 않아도 제품과 과정이 이해되어야 한다. README와 영상의 정보 설계가 구현만큼 중요하다.

### 결선 심사

- Final Panel 앞에서 라이브 데모와 질의응답
- 결선 발표를 기준으로 최종 순위 결정

**의미:** 1차용 문서 완성도와 결선용 현장 안정성을 별도로 준비해야 한다. 라이브 서비스 장애에 대비해 로컬 실행, 녹화 영상, 스크린샷을 모두 준비한다.

## 5. 공개된 평가 요소

공식 배점과 가중치는 세 사이트 어디에도 공개되지 않았다. 다만 아래 항목은 명시적으로 반복된다.

| 평가 요소 | 심사위원이 확인할 증거 | 수상권 실행 기준 |
|---|---|---|
| 문제·아이디어의 명확성 | 한 문장 문제 정의, 구체적 대상 사용자, 명확한 성공 기준 | “누구의 어떤 상황에서 생기는 어떤 손실을 줄인다”로 표현 |
| 사용자 가치·잠재 영향력 | 인터뷰, 테스트, 피드백, 전후 비교 | 기능 설명 대신 사용자의 시간·비용·오류·불편 변화 제시 |
| 실현 가능성·운영 가능성 | 데이터 출처, 비용, 배포 구조, 한계, 다음 단계 | 데모 이후 실제 운영 시 필요한 조건을 솔직히 설명 |
| 기술적 구현·안정성 | 작동하는 핵심 흐름, 테스트, 오류 처리, 재현 가능한 실행 | 한 번의 완벽한 시연보다 반복 가능한 안정적 시연 |
| 제품 완성도·UX | 온보딩, 상태 표시, 오류 메시지, 결과 이해도 | 첫 사용자가 설명 없이 핵심 작업을 완료 |
| 역할 간 협업 | Team Brief, 역할 분담, 합의·변경 기록 | Build와 Insight의 판단이 제품에 각각 반영된 흔적 |
| Codex 활용 방식 | Build Log, 계획, 위임, 검토, 테스트, 실패 복구 | 생성 코드량이 아니라 좋은 위임과 인간의 검증을 증명 |
| 검증 가능성 | 데모 영상, 테스트 결과, 사용자 피드백, 재현 절차 | 주장마다 링크·수치·관찰 결과를 붙임 |
| 지속 발전 가능성 | 우선순위 있는 로드맵, 사용자 획득·운영 계획 | 막연한 “고도화”가 아닌 다음 1주·1개월 실험 제시 |

아래 배점은 **공식 배점이 아니라**, 공개 평가 요소를 실행 우선순위로 바꾼 팀 내부용 루브릭이다.

## 6. 수상 확률을 높이는 제품 전략

### 전략 1 — 문제를 좁혀라

나쁜 정의:

> AI로 교육 문제를 해결한다.

좋은 정의:

> 발표 직전 15분 안에 피드백을 받기 어려운 대학생이 자신의 발표 영상을 올리면, 근거 문장과 함께 세 가지 개선 행동을 받는다.

좋은 문제 정의는 사용자, 상황, 현재의 손실, 원하는 변화가 한 문장에 들어간다.

### 전략 2 — 기능 목록이 아니라 핵심 흐름을 완성하라

수상권 MVP의 기본 흐름은 다음처럼 단순해야 한다.

```text
사용자 입력 → AI/서비스 처리 → 이해 가능한 결과 → 사용자의 다음 행동
```

핵심 흐름 외 기능은 15:30 전후에 동결하고, 이후에는 안정성·UX·검증·제출물에 시간을 쓴다. 메뉴가 많은 미완성 제품보다 한 흐름이 끝까지 작동하는 제품이 강하다.

### 전략 3 — 검증 결과를 제품 변경으로 연결하라

“친구에게 보여줬다”만으로는 약하다. 다음 형식으로 기록한다.

```text
가정: 사용자는 결과의 근거가 없으면 AI 제안을 신뢰하지 않는다.
테스트: 대상 사용자 3명에게 근거 표시 전/후 화면을 비교하게 했다.
관찰: 3명 모두 근거가 있는 화면을 선택했고, 2명은 원문 위치 표시를 요구했다.
변경: 결과 카드에 출처 문장과 원문 이동 버튼을 추가했다.
한계: 표본이 작아 정량 결론으로 일반화하지 않는다.
```

작은 표본이라도 가정→테스트→관찰→변경의 연결이 명확하면 검증 능력을 보여줄 수 있다.

### 전략 4 — Build Log를 경쟁 자산으로 만들어라

단순 채팅 기록 전체를 붙이는 것은 좋은 Build Log가 아니다. 판단 가능한 사건 중심으로 요약한다.

| 시각 | 목표 | Codex에 맡긴 일 | 결과 | 실패·위험 | 사람의 판단·복구 | 검증 |
|---|---|---|---|---|---|---|
| 13:20 | 핵심 API 연결 | 입력 스키마와 호출 코드 생성 | 최초 응답 성공 | 빈 입력에서 500 오류 | 입력 검증을 UI와 API 양쪽에 추가 | 정상·빈값·긴 입력 테스트 |

반드시 포함할 세 장면:

1. 계획을 세우고 작업을 나눈 장면
2. 실패를 발견하고 원인을 좁혀 복구한 장면
3. Codex의 결과를 사람이 검토·수정·검증한 장면

### 전략 5 — 심사위원이 90초 안에 이해하게 하라

README와 영상의 첫 90초는 다음 질문에 답해야 한다.

- 누구를 위한 것인가
- 어떤 문제가 있는가
- 제품으로 무엇을 할 수 있는가
- 지금 실제로 작동하는가
- 사용자에게 무엇이 달라지는가
- 왜 이 팀이 Codex를 잘 활용했다고 볼 수 있는가

### 전략 6 — 화려함보다 신뢰성을 보여라

- 입력 대기·처리 중·성공·실패 상태를 구분
- 외부 API 실패 시 이해 가능한 오류와 재시도 제공
- 샘플 데이터와 “데모 시작” 버튼 제공
- 결과가 느리면 진행 상태 표시
- 생성형 AI 결과의 출처·불확실성·한계 표시
- API Key와 개인정보를 저장소에 커밋하지 않음

역할은 책임 영역이지 작업 장벽이 아니다. Build 구성원은 Insight의 문제·검증 판단을 구현에 반영하고, Insight 구성원은 실제 제품과 테스트에 직접 기여해야 한다.

## 9. 결선 발표 가이드

공식 발표 시간은 세 사이트에 명시되지 않았다. 현장 발표 시간이 정해지면 아래 3분 구조를 비례 축소·확대한다.

| 구간 | 권장 시간 | 내용 |
|---|---:|---|
| 문제 | 30초 | 사용자, 상황, 현재 손실, 왜 중요한가 |
| 검증 | 20초 | 어떤 가정을 누구에게 어떻게 확인했는가 |
| 라이브 데모 | 80초 | 입력→처리→결과→다음 행동 한 흐름 |
| 구현·Codex | 25초 | 기술 구조, Codex 위임·복구·검증의 대표 사례 |
| 가치·가능성 | 25초 | 관찰된 변화, 운영 조건, 다음 실험 |

### 발표 원칙

- 첫 문장은 팀 소개가 아니라 사용자 문제로 시작
- 슬라이드보다 제품 화면을 오래 보여줌
- 기능 세 개를 나열하지 말고 하나의 사용자 여정을 완주
- 숫자는 출처와 표본을 함께 말함
- 실패와 한계를 숨기지 말고 어떻게 관리했는지 설명
- 네 명의 역할이 결과에 어떻게 반영됐는지 한 문장으로 정리

### 예상 질문과 답변 구조

**왜 이 문제가 중요한가?**
관찰한 사용자 상황 → 현재 대안의 한계 → 검증 결과 → 제품이 바꾸는 지표 순서로 답한다.

**ChatGPT에 그냥 물어보는 것과 무엇이 다른가?**
구조화된 입력, 도메인 데이터, 도구 실행, 검증·근거, 반복 가능한 워크플로 중 실제 차별 요소를 데모로 증명한다.

**AI가 틀리면 어떻게 하는가?**
실패 조건, 탐지 방법, 사용자 고지, 재시도·사람 검토·대체 흐름을 말한다.

**실제 운영할 수 있는가?**
데이터 권한, 비용, 지연시간, 개인정보, 책임 주체, 다음 실험을 구체적으로 답한다.

**Codex를 어디에 활용했는가?**
“코드를 만들었다”가 아니라 계획, 작업 분해, 구현, 테스트, 실패 복구, 리뷰 중 대표 사례와 사람이 내린 판단을 설명한다.

## 12. 최종 수상 공식

```text
좁고 중요한 문제
× 실제로 끝까지 작동하는 핵심 흐름
× 사용자 검증에서 제품 변경으로 이어진 근거

```

수상권 팀의 차이는 대개 마지막 기능 하나가 아니라, 이미 만든 결과를 **검증하고, 안정화하고, 심사 가능한 증거로 바꾸는 마지막 90분**에서 생긴다.
