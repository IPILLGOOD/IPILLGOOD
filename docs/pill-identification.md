작업 브랜치: `feat/123-pill-identification` · 조사일: 2026-08-31

현재 단계는 **지원/예외 상태 → 구조화 후보 검색 → 벡터 검색 필요성 평가** 중 앞의 두 단계의 서버 기반이다.
사진을 인식하는 모델이나 사용자 화면이 완성된 상태는 아니다. 이슈 #123의 전체 완료로 취급하지 않는다.

## 확인한 데이터와 제약

- [식약처 의약품 낱알식별 정보](https://www.data.go.kr/data/15057639/openapi.do)의 공식 페이지에 포함된 Swagger 명세를 확인했다.
- 최신 명세의 경로는 `https://apis.data.go.kr/1471000/MdcinGrnIdntfcInfoService03/getMdcinGrnIdntfcInfoList03`이다. 과거 v01 경로를 사용하지 않는다.
- 명세상 요청 조건은 `serviceKey`, `pageNo`, `numOfRows`, `type`, `item_name`, `entp_name`, `item_seq`, `img_regist_ts`, `edi_code`, `bizrno`이다. **모양·색상·각인·분할선은 응답 필드이지 서버 검색 파라미터가 아니다.**
- 따라서 매 검색 시 첫 페이지만 조회해 전체 검색으로 표시해서는 안 된다. 전체 외형 검색에는 페이지별 수집을 완료한 별도 참조 카탈로그가 필요하다.
- 최초 조회에서는 HTTP 403을 받았으나, 사용자가 낱알식별 전용 키를 설정한 뒤 재검증한 요청은 정상 처리됐다. 첫 페이지 3건, 두 번째 페이지 3건, 특정 품목코드 조회 1건을 현재 페이지 조회·정규화 코드로 확인했다.
- 재검증 시 API가 반환한 전체 레코드 수(`totalCount`)는 **25,387건**이다. 전체 데이터를 수집한 수치나 고유 품목 수로 해석하지 않는다. 전체 데이터의 누락률·중복·갱신 패턴은 아직 측정하지 못했다.
- API 제공 페이지는 무료·이용허락범위 제한 없음으로 안내한다. 새 저장소나 대규모 이미지 재배포를 시작하기 전에는 실제 응답 이미지의 출처와 이용 조건도 함께 확인한다.
- 회의에서 공유한 [AI 학습용 알약 이미지 데이터](https://www.data.go.kr/data/15112582/fileData.do)는 학습용 샘플 자료이며 전체 파일은 약학정보원 문의 대상으로 안내된다. 현재 약품 참조 카탈로그와 같은 것으로 취급하지 않는다.

## 이번에 구현한 것

### 공식 데이터 정규화 및 페이지 읽기

`backend/src/official-pill-catalog.ts`는 최신 공식 API의 한 페이지를 제한된 크기와 시간 내 읽는다. 키는 서버에서만 사용하며 다른 호스트로의 리디렉션은 허용하지 않는다. 자동 전체 수집이나 외부 DB 쓰기는 수행하지 않는다.

| 공식 필드 | 내부 표현 |
| --- | --- |
| `ITEM_SEQ`, `ITEM_NAME`, `ENTP_NAME` | `itemSeq`, `productName`, `manufacturer` |
| `FORM_CODE_NAME`, `DRUG_SHAPE` | `formName`, 정제/캡슐/미상, `shape` |
| `COLOR_CLASS1`, `COLOR_CLASS2` | 중복 제거 색상 목록 |
| `PRINT_FRONT`, `PRINT_BACK` | 앞/뒤 각인, 누락은 `null` |
| `LINE_FRONT`, `LINE_BACK` | 없음/일자/십자/기타/미상 |
| `MARK_CODE_FRONT_ANAL`, `MARK_CODE_BACK_ANAL` | 별도 마크 설명 |
| `ITEM_IMAGE` | 허용된 공식 호스트의 HTTPS 이미지 URL, 미지원 URL은 `null` |
| `CHANGE_DATE`, `IMG_REGIST_TS` | 공식 변경일, 이미지 등록일 |
| 응답을 읽은 시각 | `source.fetchedAt` — 공식 변경일과 구분 |

빈 각인·분할선 필드를 ‘아무 표시가 없다’고 추정하지 않는다. 미상 제형도 정제로 간주하지 않는다. 품목코드가 같아도 외형이 다른 공식 레코드를 버리지 않는다. 파싱 실패·페이지 누락·응답 페이지 불일치가 정상 무결과로 바뀌지 않도록 검증한다.

### 입력 상태와 결정적 후보 검색

`backend/src/pill-identification.ts`는 사용자 관찰 또는 향후 특징 추출기가 반환한 **구조화된 관찰 정보**를 받는다. 현재 `image_features`는 입력 출처 표시일 뿐, 사진을 분석하는 구현이 아니다. 원본 이미지·URL·자유로운 추가 필드는 받지 않는다.

| 상태 | 의미 |
| --- | --- |
| `candidates_found` | 비교할 후보가 있음. 확정이나 복용 허용이 아님 |
| `needs_retake` | 다중/겹침, 흐림·어두움, 앞뒤·모양·색상 관찰 부족 |
| `unsupported_form` | 가루·과립·액상·기타 제형, 반쪽·훼손 약 |
| `unidentified` | 약 없음, 제형 미상, 완전 수집된 카탈로그에서 무결과 |
| `not_configured` | 카탈로그 또는 API 키 미설정 |
| `unavailable` | 불완전 카탈로그, API 접근 거절·제한·통신/응답 오류 |
| `invalid_input` | 요청 형식·범위 오류 |

검색은 제형 → 색상 → 모양 → 앞뒤 각인 → 분할선 순으로 후보를 줄인다. 알려진 불일치는 제외하고, 누락은 완전 일치로 승격하지 않는다. 앞뒤 각인과 분할선은 동일한 방향으로 묶어서 비교한다. `0/O`나 부호를 임의 치환하지 않는다.

- 완전 일치/부분 일치/정보 불충분은 **비교한 특징의 일치 정도**이지 의료적 확률이 아니다.
- 여러 품목은 모두 유지하고, 같은 품목의 외형 변형은 `variants`로 묶는다.
- 결과 수 제한이 있어도 전체 후보 수와 잘림 여부를 반환한다.
- `PillCatalog`는 전체 수집 여부·행 수·버전을 요구한다. 첫 페이지나 불완전 수집은 검색에 사용할 수 없다. 실제 수집기는 페이지 중복·중단·중간 데이터 변경까지 검증한 뒤에만 `complete`를 설정해야 한다.
- 단계별 잔여 레코드 수·고유 후보 수·반환 수를 반환한다. 각인이나 품목명 등 검색 내용은 metrics에 넣지 않으며, 이 단계에서 원본/민감 로그나 분석 플랫폼을 추가하지 않는다.

### 기존 처방전의 품목코드 보존

코드 연결은 `처방전 verification.officialItemCode → MedicationPlan.itemSeq → 공식 검색/낱알 ITEM_SEQ`이다. 원문 `itemCode`는 보험코드일 수도 있으므로 정규 품목코드로 복사하지 않는다.

- 기존 서버 검증이 완료된 9자리 공식 코드만 복용약에 보존한다.
- 사용자가 약명 또는 성분을 수정했다면 이전 코드로 새 정체성을 연결하지 않는다. 수정 전 검증 정보는 근거 초안에 남으며, 활성 복용약의 코드 연결에는 사용하지 않는다.
- 기존 코드 없는 복용약·데모는 그대로 호환하며, 과거 DB를 일괄 수정하지 않는다.
- 검색 함수는 복약 계획, 복용 완료, 일정, 알림을 생성하거나 변경하지 않는다.

## 검증 방법과 한계

```powershell
node --experimental-strip-types --test backend/src/official-pill-catalog.test.ts backend/src/pill-identification.test.ts backend/src/care-repository.test.ts
npm test
npm run typecheck
npm run lint
```

`backend/test-support/pill-fixtures.ts`의 품목명·코드·특징은 **합성 테스트 데이터**다. 운영 카탈로그나 API 실패 시 대체 결과로 사용하지 않는다. 정제/캡슐 특징 검색, 앞뒤 반전, 분할선 모순, 누락, 동일 품목 변형, 미지원/재관찰 상태, 불완전 카탈로그, HTTP/파싱 오류, 품목코드 저장·재시도를 테스트한다.

현재의 검증은 검색 규칙과 상태 전이에 한정된다. 실제 사진 detection 정확도, 대표성 있는 top-1/top-3, 실제 데이터의 잔여 후보 분포는 **미측정**이다. 합성 테스트 통과율을 제품 식별 정확도로 홍보하거나 벡터 DB 도입 근거로 쓰지 않는다.

### 2026-08-31 실행 결과

- 전체 단위 테스트: 프론트 89개 + 백엔드 199개, 총 **288개 통과**. 이번 변경의 신규 테스트는 26개다.
- 프로젝트 타입 검사: `tsc -p front/tsconfig.json --noEmit --incremental false` 통과.
- 신규 낱알 테스트 파일의 별도 strict 타입 검사도 Node 타입과 ES2023 설정에서 통과.
- 프론트 lint 및 수정한 백엔드 파일의 동일 ESLint 설정 검사 통과. 백엔드에 Next 규칙을 적용한 별도 실행에서는 루트 `pages` 경로 안내 경고가 있었으며 오류는 없었다.
- 프로젝트 기본 검사 범위 밖의 기존 `care-repository.test.ts`까지 별도 strict 타입 검사를 확장하면, 기존 fixture의 `analysis: null`과 선언 타입 불일치가 확인된다. 해당 기존 fixture는 이번 기능 범위 밖이라 수정하지 않았다. 실행 회귀 테스트는 통과했다.
- 처음에는 로컬 의존성이 최신 lockfile과 달라 전체 테스트/타입 검사가 실패했다. 승인 후 `npm ci --ignore-scripts`로 의존성을 맞추고 재검증했다. 패키지 선언·lockfile·실제 키 파일은 변경하지 않았다.
- 실제 API 연결 재검증: `MFDS_PILL_API_KEY` 로딩, 첫/두 번째 페이지 조회, 특정 품목코드 조회가 모두 `connected`로 처리됐다. 표본의 모양·색상·각인·공식 이미지 URL을 정규화할 수 있었다. 키 값은 출력하지 않았으며 에이전트가 `.env.local`을 수정하지 않았다.
- 실제 응답에는 빈 각인·분할선 필드뿐 아니라 `PRINT_BACK`에 `분할선`이라는 설명이 들어오는 사례도 있었다. 연결 성공이 의미 정규화나 전체 데이터 품질 검증의 완료를 뜻하지는 않는다. 해당 표현 처리는 후속 보완 대상으로 남긴다.
- 운영 DB 쓰기, 원본 사진 전송, 브라우저 E2E, 전체 배포 빌드는 실행하지 않았다. `.env.local`을 제거해 검증을 강행하지 않았다.
- 이 변경은 #123의 1차 기반 체크포인트이며, PR 생성·이슈 종료·main 반영은 포함하지 않는다.

## 다음 단계

1. 연결 확인을 마친 API에서 여러 페이지의 표본을 조회하여 제형·색상·각인·분할선의 실제 표현, 필드 누락, 이미지 URL, 동일 품목의 외형 변형과 갱신 시점을 점검한다.
2. 표본에서 확인한 표현 차이를 정규화 규칙과 회귀 테스트에 반영한다. 이후 전체 카탈로그 수집 시 누락·중복·중간 변경을 검증할 조건을 정의한다.
3. 카탈로그 저장/동기화 방식을 확정한다. 현재 검색 엔진은 저장소 독립적이며 Firebase/Supabase/AWS나 벡터 DB를 신규 도입하지 않았다. 전체 데이터·이미지를 Worker 코드 번들에 넣지 않는다. 동기화 완료 버전의 원자적 전환, 갱신 시각/만료 정책이 필요하다.
4. 인증된 수동 특징 입력·공식 이미지 비교 UI를 먼저 연결하고 UI/통합 테스트를 추가한다. 개인 사진의 기본 저장이나 복약 계획 자동 반영은 하지 않는다.
5. 사용 가능한 실제 평가 이미지와 정답 품목코드를 확보한다. 정상·미지원·흐림·다중 약을 구분하고 top-1/top-3 및 무결과/재촬영/잔여 후보를 측정한다.
6. 실제 이미지를 외부 AI로 전송하는 특징 추출은 #61/#88의 전송 전 확인·마스킹·동의 경계를 충족한 뒤 연결한다. 필요성이 측정된 경우에만 벡터 검색을 별도 실험한다.
