현재 단계는 **지원/예외 상태 → 구조화 후보 검색 → 벡터 검색 필요성 평가** 중 앞의 두 단계의 서버 기반이다.
사진을 인식하는 모델이나 사용자 화면이 완성된 상태는 아니다. 이슈 #123의 전체 완료로 취급하지 않는다.

최종 서비스는 **사진 촬영 → 특징 자동 추출 → 공식 데이터 후보 검색 → 공식 이미지·근거 비교** 흐름을 목표로 한다. 현재 수동 특징 입력은 검색 기반을 검증하는 개발용 방법이며, 일반 사용자용 수동 입력 화면을 필수 기능으로 만들지 않는다.

## 확인한 데이터와 제약

- [식약처 의약품 낱알식별 정보](https://www.data.go.kr/data/15057639/openapi.do)의 공식 페이지에 포함된 Swagger 명세를 확인했다.
- 최신 명세의 경로는 `https://apis.data.go.kr/1471000/MdcinGrnIdntfcInfoService03/getMdcinGrnIdntfcInfoList03`이다. 과거 v01 경로를 사용하지 않는다.
- 명세상 요청 조건은 `serviceKey`, `pageNo`, `numOfRows`, `type`, `item_name`, `entp_name`, `item_seq`, `img_regist_ts`, `edi_code`, `bizrno`이다. **모양·색상·각인·분할선은 응답 필드이지 서버 검색 파라미터가 아니다.**
- 따라서 매 검색 시 첫 페이지만 조회해 전체 검색으로 표시해서는 안 된다. 전체 외형 검색에는 페이지별 수집을 완료한 별도 참조 카탈로그가 필요하다.
- 최초 조회에서는 HTTP 403을 받았으나, 사용자가 낱알식별 전용 키를 설정한 뒤 재검증한 요청은 정상 처리됐다. 첫 페이지 3건, 두 번째 페이지 3건, 특정 품목코드 조회 1건을 현재 페이지 조회·정규화 코드로 확인했다.
- 재검증 시 API가 반환한 전체 레코드 수(`totalCount`)는 **25,387건**이다. 전체 데이터를 수집한 수치나 고유 품목 수로 해석하지 않는다. 전체 데이터의 누락률·중복·갱신 패턴은 아직 측정하지 못했다.
- API 제공 페이지는 무료·이용허락범위 제한 없음으로 안내한다. 새 저장소나 대규모 이미지 재배포를 시작하기 전에는 실제 응답 이미지의 출처와 이용 조건도 함께 확인한다.
- 회의에서 공유한 [AI 학습용 알약 이미지 데이터](https://www.data.go.kr/data/15112582/fileData.do)는 학습용 샘플 자료이며 전체 파일은 약학정보원 문의 대상으로 안내된다. 현재 약품 참조 카탈로그와 같은 것으로 취급하지 않는다.

## 이번에 구현한 것

### 공식 데이터 정규화 및 페이지 읽기

`backend/src/official-pill-catalog.ts`는 최신 공식 API의 한 페이지를 제한된 크기와 시간 내 읽는다. 키는 서버에서만 사용하며 다른 호스트로의 리디렉션은 허용하지 않는다. 자동 전체 수집이나 외부 DB 쓰기는 수행하지 않는다.

| 공식 필드 | 내부 표현 |
| --- | --- |
| `ITEM_SEQ`, `ITEM_NAME`, `ENTP_NAME` | `itemSeq`, `productName`, `manufacturer` |
| `FORM_CODE_NAME`, `DRUG_SHAPE` | 원래 `formName`, 확인된 주요 제형별 정제/캡슐/미상, 원래 `shape` |
| `COLOR_CLASS1`, `COLOR_CLASS2` | 쉼표·파이프 분리 및 중복 제거 색상 목록, 투명도 표현 유지 |
| `PRINT_FRONT`, `PRINT_BACK` | 앞/뒤 `rawImprint`(NFKC·앞뒤 공백 정리), 검색용 `imprint`, 설명 포함 여부 `imprintHasDescription`; 누락·설명만 있는 각인은 `null` |
| `LINE_FRONT`, `LINE_BACK` | 없음/일자/십자/기타/미상 |
| `MARK_CODE_FRONT_ANAL`, `MARK_CODE_BACK_ANAL` | 별도 마크 설명 |
| `ITEM_IMAGE` | 허용된 공식 호스트의 HTTPS 이미지 URL, 미지원 URL은 `null` |
| `CHANGE_DATE`, `IMG_REGIST_TS` | 공식 변경일, 이미지 등록일 |
| 응답을 읽은 시각 | `source.fetchedAt` — 공식 변경일과 구분 |

빈 각인·분할선 필드를 ‘아무 표시가 없다’고 추정하지 않는다. 미상 제형도 정제로 간주하지 않는다. 품목코드가 같아도 외형이 다른 공식 레코드를 버리지 않는다. 파싱 실패·페이지 누락·응답 페이지 불일치가 정상 무결과로 바뀌지 않도록 검증한다.

수집 당시의 거친 `form` 값과 **현재 검색 지원 여부**는 별개다. `backend/src/pill-form-policy.ts`가 보존한 `formName`으로 지원 정제/캡슐·비지원·미상을 분류한다. 이 검색 정책을 변경해도 기존 스냅샷의 정규화 버전·해시·공식 필드는 덮어쓰지 않는다.

확인된 `분할선`·`십자분할선`·`마크` 설명 토큰만 검색용 각인에서 분리한다. 일반 한글 각인이나 `0/O`, `Λ`, 소수점·슬래시·부호는 그대로 보존한다. 설명에서 분할선 종류를 추정하거나 공식 `LINE_*` 값을 덮어쓰지 않는다. 제거된 설명이나 비교하지 못한 마크가 있는 후보는 완전 일치가 아닌 정보 불충분으로 남긴다.

### 입력 상태와 결정적 후보 검색

`backend/src/pill-identification.ts`는 사용자 관찰 또는 향후 특징 추출기가 반환한 **구조화된 관찰 정보**를 받는다. 현재 `image_features`는 입력 출처 표시일 뿐, 사진을 분석하는 구현이 아니다. 원본 이미지·URL·자유로운 추가 필드는 받지 않는다.

| 상태 | 의미 |
| --- | --- |
| `candidates_found` | 지원 제형이고 최소 한 면에 비어 있지 않은 문자 각인 일치 근거가 있는 비교 후보. 확정이나 복용 허용이 아님 |
| `needs_review` | 공식 제형 또는 문자 각인 근거가 부족한 보류 항목만 있음. `candidates`는 비우고 `heldCandidates`로 분리 |
| `needs_retake` | 다중/겹침, 흐림·어두움, 앞뒤·모양·색상 관찰 부족 |
| `unsupported_form` | 가루·과립·액상·기타 제형, 반쪽·훼손 약 |
| `unidentified` | 약 없음, 제형 미상, 완전 수집된 카탈로그에서 무결과 |
| `not_configured` | 카탈로그 또는 API 키 미설정 |
| `unavailable` | 불완전 카탈로그, API 접근 거절·제한·통신/응답 오류 |
| `invalid_input` | 요청 형식·범위 오류 |

검색은 제형 → 색상 → 모양 → 앞뒤 각인 → 분할선 순으로 대조한 뒤, 마지막에 후보 제시/보류를 구분한다. 명확한 비지원 공식 제형과 알려진 특징 불일치는 제외하고, 누락은 완전 일치로 승격하지 않는다. 앞뒤 각인과 분할선은 동일한 방향으로 묶어서 비교한다. `0/O`나 부호를 임의 치환하지 않는다.

- 완전 일치/부분 일치/정보 불충분은 **비교한 특징의 일치 정도**이지 의료적 확률이 아니다.
- 같은 품목의 외형 변형은 `variants`로 묶되 비교 후보와 보류 영역에서 각각 묶는다. 한 외형에 각인 근거가 있다고 같은 품목의 근거 부족 외형까지 승격하지 않는다.
- 후보 제시 가능한 방향/레코드를 우선하고, 같은 일치 등급 안에서는 일치한 비어 있지 않은 각인 면 수 → 각인 완전 일치 수 → 그 외 특징 완전 일치 수 → 품목코드/레코드 순으로 정렬한다. 정보가 부족한 후보를 확정으로 승격하지 않으며, 이 순서는 의료적 확률이 아니다. 현재 검색 규칙은 `pill-structured-v3-evidence-gate`, 제형 정책은 `pill-form-policy-v1`이다.
- 결과 수 제한은 비교 후보와 보류 항목에 각각 적용한다. 두 영역의 전체 건수·반환 건수·잘림 여부와 품목코드 합집합 건수를 따로 반환한다.
- `PillCatalog`는 전체 수집 여부·행 수·버전을 요구한다. 첫 페이지나 불완전 수집은 검색에 사용할 수 없다. 실제 수집기는 페이지 중복·중단·중간 데이터 변경까지 검증한 뒤에만 `complete`를 설정해야 한다.
- 단계별 잔여 레코드 수·고유 후보 수·반환 수를 반환한다. 각인이나 품목명 등 검색 내용은 metrics에 넣지 않으며, 이 단계에서 원본/민감 로그나 분석 플랫폼을 추가하지 않는다.

### 기존 처방전의 품목코드 보존

코드 연결은 `처방전 verification.officialItemCode → MedicationPlan.itemSeq → 공식 검색/낱알 ITEM_SEQ`이다. 원문 `itemCode`는 보험코드일 수도 있으므로 정규 품목코드로 복사하지 않는다.

- 기존 서버 검증이 완료된 9자리 공식 코드만 복용약에 보존한다.
- 사용자가 약명 또는 성분을 수정했다면 이전 코드로 새 정체성을 연결하지 않는다. 수정 전 검증 정보는 근거 초안에 남으며, 활성 복용약의 코드 연결에는 사용하지 않는다.
- 기존 코드 없는 복용약·데모는 그대로 호환하며, 과거 DB를 일괄 수정하지 않는다.
- 검색 함수는 복약 계획, 복용 완료, 일정, 알림을 생성하거나 변경하지 않는다.

- 같은 품목의 다른 외형은 두 영역에 각각 존재할 수 있다. `candidateCount`는 비교 후보의 고유 품목 수, `heldCandidateCount`는 보류의 고유 품목 수, `matchedItemCount`는 두 영역의 합집합이다. 앞의 두 건수를 단순 합산하지 않는다.
- `--limit`는 각 영역에 따로 적용한다. `truncated`와 `heldTruncated`, `returnedCount`와 `heldReturnedCount`도 분리한다. 보류가 많아서 근거 있는 후보를 화면 제한 밖으로 밀어내지 않는다.
- 단계별 `remaining`은 보류 분리 전 알려진 불일치를 제거한 레코드 수다. `unsupportedCatalogRecords`는 검색 입력과 무관하게 전체 카탈로그에서 명확한 비지원으로 제외한 레코드 수다.
- `needs_review`는 로컬 CLI의 정상 도메인 결과(exit 0)이며 실행 오류가 아니다. 보류 레코드의 약명을 정상 식별 결과나 자동 복약 계획에 사용하면 안 된다.

공식 `FORM_CODE_NAME`을 보존한 `formName`의 명시적 목록으로 판정한다. `정`으로 끝나는지, `캡슐`이 포함되는지로 추측하지 않는다. 미검토 접미 표기 역시 미상으로 남긴다.

정상 실사진 0/4는 그대로 공개한다. 현재 4건은 개발 세트라 규칙 특례나 통과 기준으로 고정하지 않았으며, 새 추출/OCR은 별도 미사용 사진에서 recall@k, 강한 후보 오답, 재촬영 대상의 후보 노출을 평가해야 한다. 상세 실행·diff는 [공개 사진 실험 기록](pill-photo-experiment.md), 팀 재현 방법은 [팀원 시작 안내](pill-photo-team-guide.md)에 정리했다.

검증 결과:

- `pill:regression` 6/6 통과, 외부 요청 0회. `pill:replay`도 외부 요청 0회이며 정상 0/4·예외 2/2를 그대로 반환했다.
- 전체 단위 테스트 **프론트 89 + 백엔드 284 = 373개 통과**, 실패·건너뜀 0개.
- 프로젝트 타입 검사, 변경 백엔드 파일 strict 타입 검사, ESLint, `git diff --check` 통과.
- `.env.local`, 카탈로그/사진 기준 파일, 프론트 화면·배포 설정은 변경하지 않았다. 생성 HTML/JSON은 `verification-artifacts/` Git 제외를 유지한다.

### 남은 로드맵

아래는 전체 로드맵이다. 사진 공개 샘플 연결의 현재 범위·남은 조건은 위 작업 로그와 실험 문서를 기준으로 한다.

1. 실제 전체 카탈로그 연결과 **각인 근거 부족 후보 보류·미상/비지원 제형 분리**, 소규모 공개 사진 평가 자료·특징 추출 계약·실험 연결을 완료했다. 사진 추출 성능은 아직 부족하므로 다음은 오류 개선과 별도 미사용 사진 평가다. 미검토 제형 45건은 임의 분류하지 않고 후속 검토 대상으로 남긴다.
2. 서비스 입력은 사진 촬영/업로드로 연결한다. 개발용 특징 입력은 테스트 수단으로 유지하되 일반 사용자용 수동 특징 입력 화면을 필수 구현하지 않는다. 사진 특징 추출과 공식 후보·이미지 비교 UI의 연결에는 아래 전송·동의 조건과 실제 이미지 평가가 필요하다. 로컬 전체 배열 검색을 운영 요청에 그대로 붙이지 않으며, 필요한 운영 저장/질의 방식은 측정에 따라 결정한다.
3. 이미지 파일은 우선 공식 URL로 관리한다. 전체 데이터·이미지를 Worker 번들에 넣지 않고, 이미지 캐시·재배포는 이용 조건과 필요성을 따로 확인한다.
4. 실제 평가 이미지와 정답 품목코드를 확보하고 정상·미지원·흐림·다중 약을 구분해 평가한다. 공식 필드 복사 예제를 사진 정확도 측정에 쓰지 않는다.
5. 일반 사용자 사진을 외부 AI로 전송하는 특징 추출은 #61/#88의 전송 전 확인·마스킹·동의 경계를 충족한 뒤 연결한다. 현재는 검수한 공개 샘플의 해시 허용 목록에 한정된 로컬 실험만 가능하다. 필요성이 측정된 경우에만 벡터 검색을 별도 실험한다.
6. 자동 갱신·수집 재개·동시 실행·운영 버전 전환은 [향후 운영 설계](pill-catalog-storage.md)를 참고하되 현재 MVP 검색 검증의 선행조건으로 두지 않는다.
