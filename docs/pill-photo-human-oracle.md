# 사람 판독 문자열 비교 — #141 비운영 진단

## 결론과 범위

사용자가 기존 validation 원본 사진만 보고 작성했다고 확인한 6제품·12면 기록을 연결했다. 동일한 `run-9EINEQ/repeat-1..3`의 최종 결합 특징에 **각인 문자열만** 교체했을 때 상위 5개 정답 포함이 16/18에서 18/18로 증가했다. 이 결과는 모델 인식 정확도 개선이 아니라 반사실적 검색 진단이다. 18개 독립 제품이 아닌 **6제품의 3회 관측**이다.

모델·프롬프트·전처리·카탈로그·후보 정렬·등급·안전 정책은 변경하지 않았다. API 호출, 사진 전송, 새로운 holdout 조건, 운영 연결도 수행하지 않았다. 실제 사람 판독값·검수자·이미지 해시·상세 경쟁 품목은 Git 제외 산출물에만 보관한다.

숫자는 정답이 해당 상위 범위에 포함된 관측 수다. 6/5/1 표는 보조 진단이며 공식 최소 표본 gate와 합격 기준을 바꾸지 않는다.

사람 조건은 모두 후보에만 존재하며 보류 전용/양쪽 존재/반환 범위 밖 사례는 없었다. 관련 상태를 구분하는 진단과 회귀 테스트는 그대로 유지된다.

## 입력·주입 규칙

- 신규 `pill-human-photo-readings.v2`는 6사례·각 2면, fixture/사진 경로/SHA, 입력 A/B 방향, 검수자·검수 일자·사진만 참고했다는 확인을 검증한다. 실제 시각은 미제공이므로 null로 보존한다.
- 직접 판독 확보 12면과 실제 문자열이 있는 11면을 구분한다. 문자 없음 1면, 사람 판독불가 0면, 사람이 기록한 비문자 로고 양성 0면이다.
- 문자 없음은 `reviewed_no_text`, 판독불가는 `reviewed_unreadable`, 미검수는 `not_reviewed`. 첫 번째도 이번 문자열-only 주입에서는 null(문자 교체 안 함)이다. 로고와 분할선은 별도 기록이며 자동으로 검색 관찰에 적용하지 않는다.
- 기록의 `비어 있음`을 각인 문자열로 넣지 않는다. 사람 원문 상태는 따로 보존하며 이 설명만 문자 없음 관찰로 구분했다. 기존 무각인/visibility/quality/안전 필드는 바꾸지 않는다.
- 모호성 비고로 대안 문자를 만들어내거나 공식 문자열로 보정하지 않는다. 실제 대안이 여러 개 기재된 경우만 배열로 보존한다. 원문의 공백을 importer가 조용히 제거하지 않는다.
- 기존 `injectOracleImprintStrings`와 실제 검색/진단 함수를 재사용한다. 항상 최종 결합 후 `observation.front/back.imprintCandidates`만 교체한다. 다른 면의 판독 상태는 사람의 판독 가능 여부로 올리지 않는다.
- 상태 계약과 충돌하면 조건 전체 미실행이다. 실패 사유를 보존하고 계획 분모를 유지하며 불완전 집계에 비율/합격을 부여하지 않는다. 이번 실제 비교에는 충돌 미실행이 없었다.
- 정답 품목코드는 검색 완료 후 진단에만 사용한다. 공식 문자열 조건은 manifest에 고정된 단일 variant 양면을 함께 매핑한다.

## 확인된 것과 아직 확인되지 않은 것

v4-v03과 v4-v06의 문자열 교체가 검색 순위를 개선했다. 저장된 원신호에서 v4-v03 A의 사람 문자열은 Vision에는 1/3회, OCR에는 0/3회 존재했다. v4-v06 B도 Vision 1/3회, OCR 0/3회다(공백 정규화 기준, 혼동문자 치환 없음). 해당 면들의 결합 truncation은 모두 false였다. 따라서 이 사례를 단순히 결합 배열 상한에서 정답을 버린 문제로 설명할 수 없다.

다만 교체는 후보 추가·제거와 복수 면 변경을 함께 포함하므로, 결과 전체를 OCR만의 인과효과나 특정 한 글자의 효과로 단정할 수 없다. 사람 판독 역시 절대적인 정답이 아니며 모호성 비고를 함께 해석해야 한다.

v4-v04는 사람과 AI의 판독 문자열이 같아 결과가 계속 3위다. 공식 문자열 조건만 1위다. 현재 정렬은 관찰 문자열 직접 일치와 혼동문자 확장 일치를 구별하며 경쟁 품목과 동률일 때 품목코드 순서도 사용한다. 이 사진에서 그 문자를 실제로 구별할 수 있다는 증거 없이 정답 품목을 1위로 올리도록 정렬을 튜닝하면 안 된다.

v4-v06 A는 사람이 문자로 읽은 형태가 공식 데이터에서는 mark 필드에 등록되어 있다. 이는 표기 체계 차이이며 사람 판독을 자동으로 틀렸다고 정정할 근거가 아니다. 이번 검수에는 확실한 비문자 로고 양성 사례가 없으므로, 앞서 제안한 로고/무각인 지침의 효과를 이 자료만으로 평가하기에는 부족하다.

## 다음 변경 하나 제안 — 이번에는 구현·API 실험하지 않음

**단일 면 OCR 프롬프트에 방향 선택 → 문자별 획 확인 → 같은 획을 색상/대비 뷰에서 대조 → 시각 근거가 있는 전체 문자열만 후보에 남기는 검수 절차를 명시하는 조건**을 제안한다. 현재 지침도 회전과 복수 후보를 안내하므로 이것이 효과적이라는 결론은 아직 아니다. 단순한 대안 문자 개수 증가나 정답 문자열 특례가 아니라, 사람이 읽은 문자열이 원신호에서 누락되는 문제에 대한 한 요인 실험이다.

- 근거: 위 두 문제 면의 저장 OCR에서 사람 문자열 포함 0/6회, 사람 문자열 주입 시 전체 recall@5 18/18. 뷰/조명/방향을 실제 실패 원인이라고 단정하지 않는다.
- 고정: 모델, Vision 지침과 입력, 전처리, 카탈로그, 결합, 검색 및 안전 정책. 약명·정답·공식 문자열은 모델에 보내지 않는다.
- 제안 성공 기준(실행 전 확정): 각 문제 면에서 사람 문자열 포함 각각 2/3회 이상, 전체 validation recall@5 18/18 및 recall@1 기존 11/18 이상, 강한 오답/재촬영 후보 노출 0. 비문자/판독불가에서 가짜 문자나 확정 증가도 별도 안전 사례로 확인해야 한다. 이 기준은 개발 실험 기준이지 운영 합격 기준이 아니다.
- 현재 사람 검수에는 판독불가/비문자 로고 양성 사례가 부족하다. 해당 안전 비교 자료의 라벨·출처가 확보되지 않으면 안전성 개선 결론은 유보한다. v5로 보충하지 않는다.
- 통과하더라도 최종 성능 확인은 새로운 미사용 자료에서 해야 한다. 이 validation과 기존 holdout의 역사적 수치를 새 성능으로 재명명하지 않는다.

## 재현·검증

Node 24에서 다음 명령을 사용한다. 서버/.env.local/키가 필요 없다. `pill:human:oracle`은 이 고정 분석의 로컬 저장 실행과 이전 audit/baseline에 한정된다.

```sh
npm run pill:human:oracle --workspace @care-atlas/backend -- --readings C:/dev/IPILLGOOD/verification-artifacts/pill-photo-audit/human-input-20260907/readings.json
npm run typecheck --workspace @care-atlas/backend
npm test --workspace @care-atlas/backend
```

출력은 Git 제외 `verification-artifacts/pill-photo-audit/human-comparison-*`의 report.json 및 report.md이며 새 폴더에 배타적으로 생성한다. Git에는 입력 계약·도구·합성 테스트·비민감 요약만 포함한다. 실제 입력은 비공개 팀 전달 대상이고 키 없이 저장 재생할 수 있다.

이번 실행에서 기존 공개 응답 84건(저장 교차 특징 72조합 포함), 이전 original/official 36행이 일치했다. 기존 계산 코드 15개 해시, 보호 입력 317개, 이전 보고서·baseline·검수표·사람 입력을 전후 검증했다. 결합 72조합을 새로 추론/재결합한 것은 아니다. 과거 v5의 2/6 보고서는 그대로 보존했다.

검사 결과:

- backend 전체 440/440 통과, skip 0 (신규 사람 판독 합성 회귀 9개 포함).
- strict TypeScript, 신규 TS 3개 ESLint, `git diff --check` 통과. ESLint는 기존 Next 설정의 루트 pages 디렉터리 안내만 출력했고 exit 0이다.
- `pill:regression` 6/6 통과, 외부 요청 0. 여기의 과거 baseline diff는 이번 변경 전후 검사와 다르며 신규 진단의 회귀로 간주하지 않는다.
- 샌드박스에서 Git 버전 기록용 자식 프로세스가 EPERM으로 차단된 최초 실행은 결과 파일을 만들지 못했다. 동일 비교를 실행 권한을 확보해 다시 실행했고 위 보존 검사와 비교가 완료됐다. API 실패가 아니다.
- 프론트 빌드·Firebase 풀사이클·원격 CI는 이번 범위에서 새로 실행하지 않았다. 테스트 로그의 requests/requestIntents는 모의 호출이며 실제 API 사용량이 아니다.

실제 비교 출력은 `human-comparison-4Ntp5e`이며 이것이 recognition 성공이나 공식 pass를 의미하지 않는다. 검수표와 JSON 입력은 해당 실행에 해시로 연결된 시점 자료로 보존한다. 실행 결과와 해석은 새 보고서에 남기며 기존 검수표의 접수 시점 문구를 현재 결과로 덮어쓰지 않는다.
