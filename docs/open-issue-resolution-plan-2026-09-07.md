### PR A — 행 단위 병합과 실패 복구

- `mergeDocumentAnalyses`는 현재 배열 위치로 약 행을 합친다. 재시도가 특정 행만 반환하거나 순서를 바꾸면 다른 약의 값이 섞일 수 있으므로 안정적인 `sourceRow`로 병합하고 중복·불명확 행은 검토 상태로 남긴다.
- 현재 누락 감지는 주로 약명·용량·횟수·시점이다. 처방일·약별 기간을 포함해 확인에 필요한 필드를 정리하고 보정 요청은 해당 행·필드로 한정한다.
- 이미 읽힌 값이 재시도에서 달라지면 조용히 교체하지 않고 원문 출처와 충돌을 보존한다. `sourceRow`와 필드 근거의 행 일치 계약도 보강한다.
- 첫 호출·보정 호출의 timeout, 잘못된 응답, 외부 분석 제공자 실패를 구분한다. 특히 보정 호출 실패로 첫 부분 결과가 사라지지 않게 한다.
- 정상 파일의 분석 실패는 저장 가능한 검토 문서로 전달하고, 인증·권한·파일 검증·저장소 장애는 각각 본래 오류로 처리한다. 실제 파일 분석을 데모 성공 결과로 바꾸지 않는다.
- 검증: 2행만 반환하는 재시도, 행 순서 변경, 중복 행, 보정 호출 실패, 전체 추출 실패, 보험코드 단독, 약별 다른 기간.

## #48 — 변경 기록과 미래 일정의 일관성

### 범위 결정

현재 사이드프로젝트 범위에는 **사용자가 확인한 변경을 기록하는 revision과 미래 알림 갱신**을 우선 권한다. 앱이 복용 중단·재개를 권고하는 기능은 추가하지 않는다.

원래 이슈의 “과거 DoseOccurrence 보존·미래 회차 취소/재생성”까지 완료하려면 #78에서 제외했던 회차 원장을 필요한 범위만큼 다시 도입해야 한다. 이를 생략한 채 원래 #48을 완료했다고 처리하지 않는다. 착수 시 원장 포함 전체 범위를 유지할지, 데모 범위로 이슈를 수정하고 원장을 별도 추적할지 정한다.

### 구현 순서

1. 논리적 plan ID와 불변 revision을 분리한다. 변경 값, 이전 revision, 효력 시점, 변경 종류, 확인자·시각·이유·근거 문서·품목 ID를 저장한다. 기존 계획은 최초 revision으로 이관하며 과거에 없던 변경 근거를 만들어내지 않는다.
2. 수정·중단·무효화·교체·재개 명령을 서버에서 처리한다. `expectedRevision`과 멱등 키를 사용하고 재개도 새 revision으로 남긴다. 확인이 필요한 필드와 서버 상태 전환 규칙은 #140과 맞춘다.
3. 현재 revision을 가리키는 포인터와 알림 재동기화 요청을 같은 트랜잭션에서 기록한다. 기존 `reminder-reconciliation.ts`의 작업·재시도 구조를 활용한다. 현재 `medicationPlanRevision()`은 일정 필드 해시이며 변경 이력을 대신하지 못한다.
4. 효력 시점 이후 일정에만 새 revision을 적용한다. 발송 직전에도 계획 상태와 revision을 재확인해 대기 중인 이전 알림의 발송을 차단한다. 이미 발송된 알림은 취소할 수 없으므로 발송 이력으로 남긴다.
5. 과거 관찰·보고서가 당시 revision 값을 읽도록 연결한다. 기존 기록은 마이그레이션 이전 출처임을 명시하고 원본을 덮어쓰지 않는다. 전체 범위라면 DoseOccurrence의 revision 참조와 미래 회차 취소/재생성을 여기에 구현한다.
6. 약 하나의 수정·등록 취소와 변경 이력 UI를 제공한다. 개인정보 삭제가 새 revision 컬렉션까지 정리하도록 기존 삭제 경로도 갱신한다.

검증: 중복 요청, 동시 수정, 미래 날짜 중단, 자정 경계, 주간 일정, PRN, 과거 보고서 불변, 알림 갱신 실패 후 재시도, 발송 경합, 다른 약 보존, 계정·건강정보 삭제.

## #141 — 새 사진 정확도를 통제된 실험으로 개선

1. v4 validation에서 면·신호별 실패표를 작성하고 모델·프롬프트·전처리·검색·카탈로그 기준선을 고정한다. v5 holdout은 동결해 튜닝이나 새 최종 평가에 재사용하지 않는다.
2. 크롭/해상도 → 회전/대비 → 각인·로고 및 복수 판독 구조화 순으로 한 요인씩 비교한다. 관찰 오류와 검색 오류를 분리하고 개선이 없는 변경은 채택하지 않는다.
3. `pill-observation.v2`를 유지하면서 출처·불확실성·충돌을 연결한다. 확실한 한쪽 각인이 반대쪽 오독으로 소실되는 사례를 검증하고 안전 게이트를 일괄 완화하지 않는다.
4. 개발에 쓰지 않은 최소 12제품·24장과 별도 예외 사례를 준비한다. 데이터 준비·라벨 검수 담당과 개발 담당을 분리하고 이미지 해시·제품 ID·공식 레코드 digest 비중복을 검사한다.
5. 새로운 평가 manifest를 추가하되 기존 6제품·12사진 계약을 느슨하게 바꾸지 않는다. 새 사진 분석 전 코드와 평가 정책, 반복 횟수, 모든 실행의 통과 판정을 고정한다.
6. 무결과·재촬영도 정상 사례 분모에 포함한다. API 실패는 별도 실행 실패로 남긴다. 모든 예정 실행의 점수·편차·호출 수·토큰·지연을 보고한다.

완료 목표는 새 세트 `recall@5 >= 5/6`(12제품이면 10/12 이상), 강한 오답 후보 0건, 재촬영 대상 후보 노출 0건이며 `recall@1/20`도 공개한다. 반복 실행 판정과 예외 표본은 결과 열람 전에 확정한다. 목표 미달이면 실패 원인을 남기고 이슈를 유지한다. 소규모 평가 통과만으로 실사용 안전성이나 배포 승인을 선언하지 않는다.

- 카탈로그 갱신, 검증 후 버전 전환, 실패 시 이전 정상 버전 유지, 최신성·출처 표시를 구현한다. 평가용 고정 카탈로그와 운영용 갱신을 분리한다.
- 비교 UI는 업로드/촬영 사진과 공식 이미지·각인·모양·색상·일치/충돌 근거를 표시한다. `candidates_found`, `needs_retake`, `unsupported_form`, `unidentified`, 시스템 장애를 구분한다.
- #141 진행 중에는 합성·공개 fixture 기반 UI 작업을 할 수 있다. 실제 사용자 사진을 외부 전송하는 기능은 #61/#88의 대체 운영 조건을 다시 정의·검증하기 전 활성화하지 않는다.
- 후보 확인은 약 식별 검토 결과로만 저장한다. 복약 계획·일정·알림을 자동 생성하지 않으며, 기존 활성 계획 변경이 필요할 때만 #48의 경로를 사용한다.
- 종료 기준: #141 평가, 품목 ID 연결, 지원/비지원 UI 회귀, 카탈로그 운영과 외부 전송·보관/삭제 조건이 모두 충족된다. 제한 데모만 완성했다면 그 범위만 보고하고 원래 #123 전체 완료로 처리하지 않는다.

## 공통 검증과 실행 순서

1. 최신 `origin/main`에서 작업별 격리 브랜치를 만든다. 브랜치 예: `codex/issue-140-document-review`, `codex/issue-48-plan-revisions`, `codex/issue-141-pill-evaluation`. 현재 로컬 수정 파일은 보존한다.
2. #140과 #48은 `types.ts`, `care-repository.ts`, 확정·알림 경로가 겹치므로 모델 계약과 PR 병합 순서를 맞춘다. 사진 추출 모듈은 별도 진행 가능하다.
3. PR별 관련 단위·통합 테스트와 타입 검사를 수행한다. 알약 변경에는 backend 타입 검사, `pill:verify`, `pill:regression`도 포함한다.
4. 통합 변경은 환경 파일이 없는 깨끗한 checkout에서 `npm run verify -- --account-full-cycle`로 기존 저장소 전체 검증을 수행한다. 유료 API 반복 평가는 별도 실험 절차와 기록으로 관리한다.
5. PR에 해결한 완료조건, 변경 전후 증거, 남은 범위를 기록한다. 일부만 해결한 PR이 상위 이슈를 자동 종료하지 않게 한다.

권장 착수 순서는 **#140 잔여 실패 재현·수정 → #48 범위 확정 및 revision 구현 → #123 통합**이며, **#141 기준선·자료 준비·실험은 담당자가 분리되면 병행**한다. 가장 먼저 만들 결과물은 #140의 현재 구현/미완료 체크표와 행 병합·보정 호출 실패 회귀 테스트다.
