# 한국어 식사/영양 자료 선별

사용자가 질환을 선택하면 LLM이 관련 네이버 블로그·공개 카페 게시글·포스팅·유튜브를 검색하고, 구체적인 내용을 담은 한국어 자료를 최대 20개 반환한다. 자료 수를 억지로 채우지 않되 검색에서 확인하고 검증한 유익한 결과는 목록에서 임의로 줄이지 않는다.

## 화면

질환 선택과 검색 버튼, 하나의 자료 목록으로 구성한다. 항목에는 한국어 제목, 플랫폼, 읽기 목적, 구체적 핵심 내용, 원문 링크를 표시한다. 네이버·유튜브·그 외 글 필터는 이미 받은 결과에서 동작하며 추가 호출하지 않는다. 주제 탭, 비교표, 공식 자료/후기 별도 영역, 영문 기본 자료, 기본 영양 카드, 상담 질문은 제거했다. 관련 컴포넌트와 CSS, 페이지의 기본 인사이트 생성도 제거했다. 다른 기능에서 사용하는 backend 영양 규칙은 유지한다.

## 확정 질환 관리

프로필의 고정 3개 선택지를 사용자별 질환 목록으로 대체했다. `ConfirmedConditionsEditor`에서 질환명과 선택 코드, 의료진 진단 확인 여부를 편집하고 프로필 저장 시 반영한다. 문서에서 확인한 질환과 기존 프로필 질환을 모두 표시하며 추가·수정·삭제를 지원한다. 건강 상태 참고 메모와 AI 추측은 이 목록으로 자동 승격하지 않는다.

서버의 `profileSchema`는 필수 목록, 항목 길이, 최대 50개, 중복 이름/ID, 사용자 확인 여부를 검증한다. 목록 필드 누락과 잘못된 JSON을 빈 목록으로 처리하지 않는다. `buildRecipientProfile`은 저장된 대상자 목록에 없는 기존 ID를 거부하며 출처·확인 시각을 클라이언트에서 받지 않는다. 변경 없는 질환은 ID와 문서 출처를 유지한다. 이름이나 코드를 수정한 질환에는 새 ID와 프로필 확인 출처를 부여해 원본 진단서 근거로 오인하지 않도록 한다. 삭제는 프로필 목록에서만 적용하고 문서 원본을 지우지 않는다.

기존 인증·동의·revision 충돌 검사를 거쳐 저장한 뒤 프로필과 식사/영양 화면을 갱신한다. 저장 성공 시 편집기는 서버 발급 ID를 다시 받으며, 충돌 시 최신 내용을 확인한 후 저장하는 기존 흐름을 따른다. LLM은 질환 등록이나 확정을 수행하지 않고, 별도 자료 검색 요청 때만 저장된 질환명·코드를 사용한다. 질환명과 코드의 의학적 정합성을 자동 검증하는 용어 사전은 이번 범위에 포함하지 않았다.

## 구조와 흐름

1. `/nutrition`은 인증된 돌봄 범위의 snapshot을 읽는다. 클라이언트에 전달하는 값은 확정 질환 ID와 표시명뿐이다.
2. 클라이언트는 `/api/nutrition/explore`에 conditionId만 보낸다. 서버는 origin, 세션, 동의, 호출 제한과 돌봄 대상자의 확정 질환 여부를 확인한다.
3. 서버가 해결한 질환명·코드로 OpenAI 웹 검색을 호출한다. 이름, 계정 ID, 문서, 약 목록은 전송하지 않는다. 질환명·코드는 외부 공급자에게 전달된다.
4. 서버는 네이버 실천 자료, 유튜브 설명, 국내 병원·학회 자료의 세 검색 관점을 전달한다. 한 요청은 40초, 중간 검색 컨텍스트, 3,000 출력 토큰, 웹 도구 3회 이내의 예산으로 제한한다. SDK create 타입이 웹 도구 호출 상한 파라미터를 지원하지 않아 호출 횟수는 프롬프트 지시이며, 시간과 출력 상한은 코드에서 강제한다. 유튜브는 한국어 자막/전사 내용이 확인된 자료만 대상으로 한다.
5. `validateNutritionArticles`가 스키마, 검색 출처 URL 일치, HTTPS, 한국어 신호, 관련성/구체성/광고 여부, 본문/자막 접근 상태를 검사한다. 직접 관련되지 않는다고 스스로 밝힌 요약도 차단한다. 네이버가 본문 접근을 막은 경우에만 구체적인 한국어 검색 미리보기를 `검색 미리보기`로 표시해 링크 발견용으로 허용한다. 유튜브는 계속 한국어 자막을 확인한 영상만 허용한다.
6. 최종 결과는 최대 20건이며, 적은 결과를 허구나 번역 자료로 채우지 않는다. 원문 발췌와 내부 선별 신호는 클라이언트나 결과 캐시에 반환하지 않는다.
7. 공개 질환별 결과만 24시간 캐시하고 개인 HTTP 응답은 `private, no-store`로 반환한다. 현재 검색·검증 규칙에는 `nutrition-exploration-ko-discovery-v11`을 사용해 이전 결과를 재사용하지 않는다. 같은 서버 인스턴스에서 같은 질환의 동시 요청은 하나의 진행 중 검색을 공유한다.
8. 문서 분석과 별도의 `nutritionSearch` 제한을 사용한다. 성공 로그에는 처리 시간과 결과 개수만, 실패 로그에는 단계·안전한 오류 코드·처리 시간만 남긴다. 질환명과 공급자 원문 오류는 기록하지 않는다.

## 오류와 절충

- 검색 시에만 외부 호출한다. 첫 화면 로딩에 AI를 기다리지 않는다.
- 실패/40초 서버 시간 초과는 503, 횟수 제한은 429다. 브라우저는 50초에 중단한다. 페이지 메모리에 있는 이전 결과는 유지하며 질환을 바꾸는 동안 응답이 와도 요청한 질환에 저장한다.
- 검색 0건과 오류를 구분한다. 외국어 기본 자료로 대체하지 않는다. 0건도 하루 캐시된다.
- 영양 검색은 6회/분의 별도 제한을 사용해 문서 분석 요청과 서로 차단하지 않는다. 데이터 캐시에는 기존 Next 설정의 `unstable_cache`를 사용한다.
- 언어·본문 접근·관련성·광고 판단은 LLM의 자체 보고와 발췌에 의존한다. 한국어 문자 검사는 보조 신호이며 원문 전체 언어를 독립적으로 판별하지 않는다. 출처 URL 일치도 요약 정확성이나 의학적 검수를 증명하지 않는다.
- 별도 크롤러/유튜브 자막 API는 없다. 검색 도구가 접근할 수 없는 블로그나 자막은 제외되어 결과가 적어질 수 있다. 부실한 자료로 개수를 채우는 대신 선택한 절충이다.
- 새 식단 처방이나 복용약 안전성 판단은 하지 않는다. 페이지의 약물 카운트와 기본 인사이트 계산을 제거했다. 공통 snapshot 조회 자체에는 약 데이터가 포함될 수 있지만 클라이언트 목록과 검색 입력에는 전달하지 않는다.

## 검증과 다음 평가

관련 단위/라우트 테스트는 한국어 번역으로 위장한 외국어 분류, 언어 불명, 영문 출력, 본문 미확인, 유튜브 자막 조건, URL 중복·위험 링크, 8건 상한, 인증·동의·확정 질환 검사와 실패 응답을 다룬다. 관련 단위/라우트 테스트 12개, 워크스페이스 타입 검사, 프런트 린트가 통과했다. 브라우저 검증은 합성 한국어 응답으로 목록, 영상 링크, 질환 전환, 오류/0건, 390px·1440px overflow 없음과 44px 이상 버튼을 확인했다.

실제 검색 API 호출은 앞선 자동 승인 검토의 외부 질환 전송 차단 이후 재시도하지 않았다. 따라서 실제 자료 선정 품질이나 자막 검색 성공률을 검증 완료로 볼 수 없다. Firebase 전체 앱 검증도 Java 런타임 부재로 미완료다.

실검색 가능 시 평가할 항목은 다음과 같다.

- 원문이 한국어이며 링크가 해당 글/영상을 직접 가리키는가?
- 요약의 구체적인 내용이 본문·자막과 일치하는가?
- 기본 상식의 반복보다 실제로 얻을 정보가 있는가?
- 광고·중복·과장 자료가 걸러지는가?
- 사용자가 원문을 열어보고 유익하다고 평가하는가?

이 지표의 성능 수치는 아직 측정하지 않았다.

## 503 진단

`nutrition_exploration_failed` 로그에는 이제 단계(`care_scope`, `snapshot`, `configuration`, `search`)와 고정 오류 코드, 확인 가능한 공급자 HTTP 상태만 남긴다. 키·원본 응답·임의 오류 메시지는 기록하지 않는다. `key_format`은 키 값에 대입문, 공백 또는 중복 접두어가 포함된 붙여넣기 오류다. 실행 설정인 `front/.env.local`에 발급받은 원본 키만 넣고 개발 서버를 재시작해야 한다. 키를 추측해서 복구하지 않는다. `provider_auth`는 인증, `provider_request`는 모델/요청 설정, `provider_quota`는 한도, `provider_connection`은 네트워크 오류를 구분한다. 이 진단·라우트·자료 검증 관련 테스트 16개가 통과했다.

공급자 429는 이제 HTTP 429로 반환한다. `rate_limit_exceeded`와 `insufficient_quota`를 구분하고, 식별 가능한 코드가 없는 429는 `provider_limit_unknown`으로 남긴다. 예전 로그의 `provider_rate_limit`만으로 상세 제한 원인을 확정할 수 없다. 일시 제한/미분류 제한에는 공급자의 유효한 Retry-After를 사용하며 없으면 앱 정책으로 60초 대기한다. 클라이언트는 대기 동안 검색 버튼을 비활성화하고 자동 재호출하지 않는다. 명시적인 quota 오류에는 재시도 대기를 제안하지 않고 사용 한도 확인 메시지를 유지한다. 공급자 계정의 한도 자체를 변경하거나 해결한 것은 아니다.

## 검색 확대의 의도와 검증 범위

직접 검색 대비 목표는 여러 검색어·플랫폼을 오가는 수고를 줄이는 것이다. 첫 검색에서는 제목과 검색 미리보기를 활용해 관련 자료를 최대 8개까지 빠르게 모은다. 질환의 원인·증상·진단·치료 같은 일반 정보는 제외하고, 질환과 연결된 영양소·식재료·식단·조리·장보기·외식 자료만 요청한다. 네이버 검색 API를 직접 연동한 것은 아니며 OpenAI 웹 검색에서 네이버 블로그·공개 카페·유튜브 도메인을 지정한 검색어를 사용한다.

새 프롬프트의 실제 원문 충실도, 플랫폼 구성비와 선별 품질 개선은 아직 측정하지 않았다. 기능 검증과 실제 검색 품질 평가는 별개다. 사용자가 검색 자체는 동작한다고 확인했지만 이번 검색 확대의 유효성까지 확인한 것은 아니다.

한 번의 버튼 클릭은 공급자 요청 1회이며 SDK 자동 재시도는 0회다. 검색 컨텍스트는 low, 출력은 최대 2,600토큰, 웹 도구는 프롬프트상 최대 4회다. 실용 식단·네이버 경험·유튜브·병원 영양자료로 검색 관점을 나눠 최대 8개 후보를 확보한다. 후보별 정독과 세부 품질 판정은 생략하고, HTTPS·검색 출처 일치·한국어·질환명·중복 여부와 캠페인·사업 소개 여부는 서버에서 검사한다. 이 예산은 공급자 계정의 실제 RPM·TPM·사용 한도를 변경하지 않는다.

rate_limit 로그는 원문 오류를 출력하지 않고 TPM/RPM 문구에서 tokens/requests/unknown과 Limit/Used/Requested 숫자만 추출한다. x-ratelimit의 요청·토큰 limit/remaining 숫자도 기록한다. 키, 조직 ID, 원문 메시지나 검색 내용은 로그에 복사하지 않는다. 다음 실제 실패에서 한도 차원을 확인하기 위한 진단이다.
