# 알약 식별 #123 — 향후 운영용 카탈로그 저장·동기화 설계

작성일: 2026-08-31 · 기준 브랜치: `feat/123-pill-identification` · 기반 커밋: `4daef08`

**상태: 향후 운영 단계의 참고 설계안. 현재 MVP의 선행 구현 목록이 아니다.**
사용자와 범위를 재검토한 결과, 먼저 JSON 파일 기반 수집·검증·오프라인 후보 검색을 구현했다. 사용 방법과 현재 범위는 [로컬 후보 검색 안내](pill-catalog-local.md)를 따른다. 이 문서 3~8절의 DB 구조·중간 재개·운영 전환 등은 후속 검토 사항이다.
서비스 입력은 사진 촬영/업로드를 목표로 하며, 수동 특징 입력은 개발 검증용이다. 초기안의 수동 입력 UI는 일반 사용자용 필수 기능으로 채택하지 않는다.
실데이터 표본 점검과 기존 검색 동작은 [알약 식별 작업 기록](pill-identification.md)에 정리되어 있다.

## 1. 이번 단계의 결론

- 사용자 복약 데이터는 기존 Firebase에 유지한다. 공개 낱알 카탈로그는 별도 수명주기의 참조 데이터로 관리한다.
- 현재는 **두 차례 수집·검증 → 로컬 JSON 파일 → 기존 순수 검색 함수**를 연결한다. SQLite 어댑터 구축을 검색 검증의 선행조건으로 두지 않는다.
- 운영 저장소는 현재 Cloudflare 배포 환경에 맞는 **D1을 우선 검증할 후보**로 둔다. 계정 요금제·용량·조회 비용·검색 결과 동등성 검증 전에는 도입 확정으로 취급하지 않는다.
- 수집 중 데이터와 검색에 공개된 데이터를 분리한다. 새 수집이 실패하면 허용된 최신성 범위 안의 이전 정상 버전을 유지한다.
- 이미지 파일은 내려받지 않고 공식 이미지 URL과 메타데이터만 저장한다. 벡터 DB, 사진 특징 추출, 사용자 화면, 복약 계획 변경은 이 단계의 범위 밖이다.

## 2. 현재 코드에서 확인한 제약

| 확인한 코드 | 설계에 미치는 영향 |
| --- | --- |
| `front/wrangler.jsonc`, `front/open-next.config.ts` | Next/OpenNext 앱을 Cloudflare Worker로 배포한다. 현재 D1/R2 바인딩은 없다. |
| `front/custom-worker.ts` | 매분 알림 발송·계정/데모 정리 작업을 실행한다. 여기에 수백 페이지 전체 수집을 붙이지 않는다. |
| `backend/src/firebase-admin.ts`, `backend/src/firestore-rest.ts` | 기존 사용자 데이터는 Firestore 사용. 현재 자체 REST 어댑터의 질의 연산자는 동등/범위 비교이고, 각인 부분 문자열·양면 조합 검색 계약은 없다. Firestore 제품 전체의 기능 한계라는 뜻은 아니다. |
| `backend/src/official-pill-catalog.ts` | 고정 공식 API에서 최대 100건씩 읽는다. 페이지/응답 검증은 있지만 전체 수집·저장·재개 기능은 없다. |
| `backend/src/pill-identification.ts` | 전체 배열과 `totalCount`가 일치하는 완전 카탈로그를 대상으로 검색한다. 매 요청마다 전체 데이터를 적재하는 운영 구조로 그대로 사용하지 않는다. |

### 저장소 선택 범위

| 선택지 | 이 프로젝트에서의 판단 |
| --- | --- |
| 로컬 SQLite | 후속 저장/검색 요구가 복잡해지면 검토할 선택지. 현재는 JSON 파일로 검색을 검증하며 SQLite 구현이 먼저 필요한 것은 아니다. |
| Cloudflare D1 | 현재 배포 환경과 연결하기 쉬운 운영 후보. SQLite 설계와 공통으로 쓸 SQL 범위를 검증하되, 로컬 SQLite 테스트만으로 D1 호환성을 보장하지 않는다. |
| 현재 Firestore 어댑터 | 사용자 데이터 저장에는 유지한다. 카탈로그 검색을 넣으려면 질의/색인 계약을 별도로 보완해야 하므로 이번 첫 구현에서는 확장하지 않는다. |
| Supabase/PostgreSQL, AWS의 별도 DB | 이번 코드에는 연결 구성이 없다. D1 검증 결과나 팀 운영 요구에 따라 재검토할 수 있으나 새 서비스 계정·배포 체계를 지금 도입하지 않는다. |
| 벡터 DB | 공식 품목코드·모양·색상·각인으로 찾는 기준 검색을 만든 뒤 실제 사진 평가에서 필요성을 판단한다. 일반 카탈로그 저장과 별도 의사결정이다. |

이는 현재 코드와 운영 부담을 고려한 제안이지, 특정 제품이 보편적으로 더 정확하거나 저렴하다는 결론이 아니다.

## 3. 저장할 데이터와 식별 단위

다음은 논리 구조이며 실제 SQL 마이그레이션은 후속 구현에서 작성한다.

| 논리 데이터 | 필수 정보 / 불변 조건 |
| --- | --- |
| 수집 실행 `catalog_runs` | 실행 ID, 상태, 시작/종료 시각, API 경로·조회 범위, 페이지 크기, 정규화/스키마 버전, 예상 행 수, 오류 분류. 재개 시 설정이 달라지면 같은 실행을 이어 쓰지 않는다. |
| 페이지 기록 `catalog_pages` | `(runId, passNo, pageNo)` 고유 키, 수신 행 수, 응답의 전체 행 수, 페이지 내용 지문, 완료 시각. 동일 페이지 재처리는 누적 삽입하지 않는다. |
| 수집 레코드 | `(runId, passNo, pageNo, rowIndex)` 고유 키, 품목코드, 정규화된 `OfficialPillItem`, 내용 지문. 서로 다른 페이지 위치의 중복 행은 검증 전에 조용히 제거하지 않는다. |
| 검증된 스냅샷 `catalog_snapshots` | 스냅샷 ID, 근거 실행/회차, 전체 행 수, 고유 품목 수, 내용 지문 집합의 해시, 정규화/스키마 버전, 검증 시각. 준비 완료 후 내용은 불변이다. |
| 활성 포인터 `catalog_active` | 단일 슬롯의 스냅샷 ID, 이전 스냅샷 ID, 증가하는 revision, 전환 시각. 검색에 사용할 버전의 단일 기준이다. |

- `itemSeq`는 품목 연결 키이지 레코드의 유일 키가 아니다. 같은 품목의 다른 외형을 보존한다.
- 내용 지문은 정규화된 공식 필드에 대해 결정적으로 계산한다. 조회할 때 달라지는 `source.fetchedAt`은 제외하고, 공식 변경일·이미지 URL·앞뒤 원래 각인·설명 여부 등 보존된 공식 정보는 포함한다. 비교 시 정규화 버전도 같아야 한다.
- 이 지문은 **현재 보존하는 필드의 변화**를 감지한다. 저장하지 않는 API 필드나 원본 응답 바이트 전체가 동일하다는 증거는 아니다.
- 동일 지문의 발생 횟수도 유지한다. API의 행 수, 서로 다른 레코드 수, 고유 품목코드 수를 별도 집계한다.
- 공식 필드 누락은 `null`/`unknown`으로 저장한다. 검색용 정규화 필드와 보존 필드를 구분하고, 각인 없는 면·마크·분할선을 혼동하지 않는다.
- 2회 수집 자료는 검증용 임시 데이터로 구분한다. 운영 검색에는 검증된 한 회차만 사용하며, 임시 자료 정리 정책은 정상 버전 보존과 별개다.
- 사용자 ID, 처방전, 복용 기록, 사용자 촬영 사진은 이 저장소에 넣지 않는다. API 키·키가 들어간 URL·원문 오류 응답도 저장하지 않는다.

## 4. 전체 수집과 검증

흐름: **수집 중 → 검증 중 → 사용 준비 완료 → 활성 포인터 전환**. 실패/검토 필요 상태에서는 전환하지 않는다.

1. **사전 검사:** 키 설정, 조회 범위, 출력 경로, 수집 상한을 검증한다. 로컬 산출물은 Git 제외 경로에 둔다. 자동 실행 대신 명시적 실데이터 실행 옵션을 요구한다.
2. **첫 번째 순회:** 1페이지에서 얻은 전체 행 수와 페이지 크기로 끝 페이지를 계산한다. 이후 모든 응답의 페이지 번호·행 수·전체 행 수를 확인한다. 예상하지 못한 빈/짧은 페이지, 전체 수 변경, 파싱 실패는 공개 중단 사유다.
3. **페이지 단위 저장:** API 호출은 DB 트랜잭션 밖에서 수행한다. 한 페이지의 데이터와 완료 표시는 함께 확정하여, 중단 후 완료 표시만 있고 데이터가 없거나 같은 페이지가 중복 삽입되지 않게 한다.
4. **재개:** 마지막 연속 완료 페이지 다음부터 이어 읽되, 저장된 페이지 지문·설정·실행 만료를 검증한다. 실행 시간이 허용 범위를 넘었거나 설정이 바뀌면 새 실행으로 시작한다. 재개했다고 검증 순회를 생략하지 않는다.
5. **두 번째 전체 순회:** 동일 범위·정규화 버전으로 다시 읽어, 순서와 무관한 `(내용 지문, 발생 횟수)` 집합 및 전체 행 수를 첫 순회와 비교한다. 행 수가 같아도 내용이 바뀌면 준비 완료로 만들지 않는다.
6. **검토:** 반복 페이지, 정확히 같은 행의 반복, 동일 품목의 다른 외형을 구분한다. 중복이 합법적인 원천 데이터인지 페이지 흔들림인지 해소하지 못한 실행은 `검토 필요`로 보류한다. 행 수를 맞추려고 잘라내거나 채우지 않는다.
7. **스냅샷 확정:** 저장된 행과 집계·지문을 다시 검증하고 불변 스냅샷을 만든 뒤에만 전환 대상이 된다. 전체 수가 갑자기 0인 응답 역시 기존 데이터를 빈 카탈로그로 자동 교체하지 않고 검토 대상으로 둔다.

표본 당시 25,387행과 페이지 크기 100을 기준으로 계산하면 한 순회는 254요청, 두 순회는 **508요청**이다. 재시도·추가 검증 호출은 별도이며, 실제 키의 잔여/일일 한도는 아직 확인하지 않았다. 이번 설계 작업에서는 전체 수집을 실행하지 않았다.

**보장 한계:** 현재 확인한 API 명세에는 시점 고정 스냅샷 토큰이나 정렬 고정 파라미터가 없다. 두 번의 순회가 같아도 원천 데이터의 시점 일관성·완전성을 수학적으로 증명하지 못한다. 검증 수준은 `two_pass_consistent`처럼 명시하고, `complete`를 사진 식별 정확도나 식약처의 무누락 보증으로 설명하지 않는다. 안정적으로 수집할 수 없으면 자동 공개를 보류하고 고정 파일 제공 등 대안을 확인한다.

### 실패·재시도 정책

- 첫 구현은 현재 페이지 읽기의 오류 분류를 재사용하여 안전하게 중단하고, 완료된 페이지를 보존한다.
- 현재 `api_error`에는 통신·파싱 등 여러 실패가 함께 포함된다. 모두 일시 장애라고 보고 자동 재시도하지 않는다.
- 자동 재시도는 후속 보완에서 안전한 상태 분류와 정제된 `Retry-After` 정보를 제공한 뒤, 일시적 네트워크/서버 장애·호출 제한에만 횟수/총시간 상한을 두고 구현한다. 접근 거절·잘못된 응답은 무한 재시도하지 않는다.
- API/DB 오류는 정상 무결과로 바꾸지 않는다. 로그에는 실행 ID, 페이지 번호, 건수, 소요 시간, 정제된 오류 코드만 남긴다.

## 5. 버전 전환·복구·최신성

- 전체 카탈로그를 기존 활성 데이터 위에 덮어쓰지 않는다. 준비 완료된 새 스냅샷을 만든 다음 포인터만 원자적으로 전환한다.
- 운영에서 동시 실행을 허용한다면 만료되는 실행 잠금과 증가하는 fencing token을 둔다. 만료된 작업자가 나중에 돌아와 활성 버전을 바꾸지 못하게 한다.
- 포인터 전환은 예상 revision·유효한 실행 권한·대상 스냅샷 준비 상태를 함께 검사하는 조건부 갱신으로 수행한다. 반영 행 수가 0이면 충돌이며 성공이 아니다. 초기는 단일 수집기만 지원하더라도 이 전환 계약은 유지한다.
- D1 어댑터에서는 준비된 SQL과 `batch()`의 원자성을 사용하되, 로컬 SQLite의 임의 트랜잭션 콜백을 그대로 지원한다고 가정하지 않는다. SQL 오류와 조건부 갱신의 0행 결과도 구분한다. [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)
- 응답 중 버전이 바뀌어도 섞이지 않도록 검색 시작 시 스냅샷 ID를 고정하고 모든 후속 조회에 적용한다. D1 복제 읽기를 도입한다면 활성 포인터와 데이터의 일관성까지 별도 검증한다.
- 새 실행 실패 시 기존 포인터를 유지한다. 단, `verifiedAt` 기준 최대 허용 경과 시간을 넘긴 카탈로그는 `unavailable`로 처리한다. 마지막 정상 버전을 무기한 최신으로 표시하지 않는다.
- 갱신 주기·경고 시점·최대 허용 경과 시간은 **운영 확정 전 설정해야 하는 정책 값**이다. 첫 로컬 구현은 테스트용 시간을 주입해 경계만 검증하고, 근거 없는 운영 기본값을 만들지 않는다. 공식 `changedAt`이 오래됐다는 이유로 개별 약을 오래된 수집 데이터라고 판단하지 않는다.
- 내용이 이전과 같아도 검증 실행 이력은 남긴다. 전체 재검증 후에만 검증 시각을 갱신할 수 있으며 기존 행의 `source.fetchedAt`을 새 값으로 꾸미지 않는다.
- 롤백은 보존 중인 검증 완료·최신성 조건 충족 스냅샷으로 포인터를 다시 전환한다. 활성/직전 버전이나 진행 중인 검색이 참조하는 버전은 정리하지 않는다. 초기 구현에서는 자동 삭제를 넣지 않고, 운영 보존 기간·검색 최대 시간에 따른 안전한 정리 조건을 이후 정한다.

## 6. 현재 검색 엔진과 연결할 때 지킬 계약

현재 `PillCatalog`는 전체 배열을 뜻한다. **DB에서 일부만 읽고 `totalCount = items.length`, `completeness = complete`로 설정해서는 안 된다.**

첫 로컬 검증에서는 완전 스냅샷을 기존 순수 함수로 읽어 기준 결과를 얻는다. 운영용 질의는 다음을 분리한 별도 저장소 계약으로 구현한다.

1. 활성 스냅샷 메타데이터 조회: 버전, 검증 상태·시각, 전체 행 수.
2. 그 스냅샷 안에서의 후보 검색: 입력 검증, 필터, 전체 후보 수, 반환 제한, 단계별 집계.
3. 선택된 품목의 모든 일치 외형·공식 이미지·근거 조회: 같은 스냅샷 ID 사용.

운영 SQL/어댑터의 완료 조건:

- 기존 입력 예외 상태, `unknown` 처리, 앞뒤 반전, 각인과 분할선의 면 대응을 보존한다.
- 각인 정규화는 현재 JS의 NFKC·대문자화·공백 제거와 같아야 한다. `0/O`나 부호를 자동 치환하지 않는다.
- 현재 각인 비교는 완전 일치만이 아니라 **공식 각인에 관찰 문자열이 포함되는 경우**도 허용한다. 동등 조건 색인만으로 후보를 먼저 잘라내지 않는다.
- `%`·`_`가 실제 각인에 포함될 수 있으므로 SQL `LIKE`에 그대로 넣어 와일드카드로 해석하지 않는다. 리터럴 부분 문자열 비교 또는 정확한 이스케이프와 바인딩을 검증한다. D1은 `LIKE/GLOB` 패턴에도 길이 제한이 있으므로 API 입력 범위를 그대로 지원한다고 가정하지 않는다. [D1 제한](https://developers.cloudflare.com/d1/platform/limits/)
- SQL 사전 필터를 둔다면 최종적으로 일치할 수 있는 모든 행의 상위집합이어야 한다. 미상 공식 필드·모양 `기타`를 불일치로 제거하지 않는다.
- 결과 `LIMIT`을 먼저 적용해 후보 수를 축소하지 않는다. 품목별 묶음·단계별 잔여 행 수·동일 품목 외형·안정적 정렬이 기준 함수와 같아야 한다.
- 예산 초과로 일부만 읽었으면 전체 검색 성공/무결과로 응답하지 않는다. 완전한 결과를 만들 수 없다는 상태를 반환한다.
- 현재 후보 생성은 각인 exact·제한적 혼동 확장·partial 근거를 우선하고, 제형·모양·색상·분할선 불일치는 후보를 삭제하지 않고 `conflicts`로 남겨 재정렬한다. 운영 SQL 사전 필터도 이 후보 상위집합을 보존해야 한다. 향후 사진의 조명 보정, 각인 전용 OCR, 이미지 유사도는 **별도 추출·검색 규칙 변경과 평가**로 다루며 저장소 교체에 섞지 않는다.

## 7. 비용·배포 검증 기준

조사일 기준 D1 Free의 일일 한도는 읽기 500만 행, 쓰기 10만 행이다. 반환 건수가 아니라 스캔 행 수가 읽기에 영향을 주고, 색인 갱신과 삭제도 쓰기 비용에 포함된다. 전체 수집의 2회분·페이지 기록·색인·구버전 정리를 합산해야 하므로 **약 2.5만 건이니 무료라는 결론은 내리지 않는다.** [D1 요금 기준](https://developers.cloudflare.com/d1/platform/pricing/)

D1은 Free DB당 500MB, 쿼리당 바인딩 100개, Worker 호출당 쿼리 50개(Free)/1,000개(Paid) 등의 제한이 있다. API 한 페이지 100건을 그대로 하나의 거대한 SQL이나 단일 Worker 실행에 넣지 않고, 실제 열 수·문장 수에 맞게 나눈다. [D1 제한](https://developers.cloudflare.com/d1/platform/limits/)

Cloudflare Workers의 메모리 한도는 128MB다. 전체 카탈로그 JSON을 번들에 넣거나 매 검색 시 전체 배열을 생성하는 구조는 채택하지 않고 실제 런타임에서 확인한다. [Workers 제한](https://developers.cloudflare.com/workers/platform/limits/)

운영 도입 전에 측정할 값:

- 1회 수집/검증의 API 요청 수·시간·실패/재개 횟수, 실제 키의 호출 한도.
- 전체 스냅샷·검증용 임시 데이터·색인·보존 버전을 합친 저장 용량.
- 대표 입력과 최악 입력의 조회 행 수·쓰기 행 수·쿼리 수·응답 크기, p50/p95 지연.
- Worker CPU/메모리와 동시 검색/수집 시 영향. 색인 추가의 읽기 절감과 쓰기 증가를 함께 비교.
- 기준 함수와 로컬 SQLite/D1 어댑터 결과의 동등성. 로컬 D1 테스트는 운영 DB를 건드리지 않는 별도 설정으로 수행할 수 있다. [D1 로컬 개발](https://developers.cloudflare.com/d1/best-practices/local-development/)

일반 사용자 검색 요청에서 전체 수집을 시작하지 않는다. 운영 수집 스케줄/작업 실행 환경은 위 측정 후 별도로 구성하며, 기존 매분 알림 작업과 분리한다.

## 8. 초기 운영 확장안 — 현재 MVP 이후 재검토

| 순서 | 구현 범위 | 완료 기준 |
| --- | --- | --- |
| 1 | 수집·검증 순수 로직, 저장소 계약, 가짜 API/저장소 테스트 | 누락/중복/순서 변화/동일 행 수의 내용 변화/중단/재개를 구분하고, 검증 실패 버전은 활성화되지 않음 |

| 4 | 운영 질의 계약과 D1 로컬 검증 | 기존 검색 결과/근거/집계 동등성, 바인딩/쿼리/메모리 제한 검증. 계정·요금제·최신성/보존 정책 확인 후 운영 도입 결정 |

필수 회귀 사례에는 마지막 페이지 누락, 재개 시 동일 페이지 중복 저장, 같은 `itemSeq`의 다른 외형, 빈 공식 필드, 같은 행 수에서 품목 교체, 양면 뒤집힘, 문자 부호/부분 일치, DB 쓰기 중단, 동시 활성화 충돌, 활성 버전 없는 최초 실패, 마지막 정상 버전 만료를 포함한다.

위 표는 초기 운영 확장안으로 보존한다. **현재 실제 구현은 JSON 파일을 이용하며, SQLite/D1 구현보다 실제 데이터 후보 검색 검증을 우선한다.** 운영 D1 생성·바인딩/비밀값 추가·배포·스케줄 설정은 별도 확인 뒤 진행한다.
