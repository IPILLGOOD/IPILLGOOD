# 회원 탈퇴·복구 (#99)

## 제품 정책

2026-08-28 사용자가 정한 정책을 반영했다. 탈퇴하면 즉시 서비스 이용을 차단하고 계정과 돌봄 기록을 **3개월간 소프트 삭제** 상태로 보관한다. 그 안에 같은 Google 계정으로 로그인하면 복구 절차를 안내한다. 명시적으로 복구를 완료하지 않은 계정은 만료 후 하드 삭제한다. 로그인·안내 열람·취소만으로 복구되거나 삭제 기한이 연장되지는 않는다.

3개월은 **한국 시간의 달력 기준**이다. 해당 날짜가 없는 달은 말일로 보정하며 시각은 유지한다(8월 31일 → 11월 30일, 11월 30일 → 다음 해 2월 28일 또는 29일). 만료 시각부터 복구를 거부하고 다음 Cron에서 영구 삭제를 시작한다. 실패한 작업은 재시도하며 실제 데이터가 남아 있으면 삭제 완료로 표시하지 않는다.

정책 버전은 `withdrawal-three-months-v1`이며 `backend/src/account-deletion-policy.ts`에서 관리한다. 기존 `ACCOUNT_DELETION_POLICY_JSON` 승인 대기 게이트는 제거했다. 이는 #99의 탈퇴·복구 방식에 대한 제품 결정이며, #62의 다른 데이터 보관 기준이나 #88의 법률·동의·대리권 검토 전체가 완료됐다는 뜻은 아니다.

## 사용자 흐름

프로필 하단 `계정 관리 → 회원 탈퇴`에서 안내 → Google 본인 확인 → 최종 확인 → 처리 결과로 이어진다. 모바일 헤더에서도 프로필에 진입할 수 있다. 건강정보만 초기화하는 기능과 구분하며 데모 계정에서는 비활성화한다.

탈퇴 정리 후 브라우저 인증·알림·앱 캐시를 정리하고 로그인 화면으로 이동한다. 탈퇴한 계정으로 다시 로그인하면 `/account/recovery`에서 탈퇴 일시, 복구 기한, 되살아날 기록, 알림 재설정 안내를 표시한다. 체크박스와 `확인하고 계정 복구` 버튼으로 별도 확인한다. 취소하면 로그인 화면으로 나가며 삭제 예약은 그대로 유지한다.

복구하면 기존 프로필·문서·복약·안부 기록을 다시 이용할 수 있다. 모든 기기의 이전 로그인과 알림 구독은 해제된 상태를 유지한다. 알림은 사용할 기기에서 다시 설정해야 한다.

## 인증과 데이터 경계

클라이언트는 UID/recipientId나 삭제 기한을 지정할 수 없다. 탈퇴 시작 시 서버의 서명된 세션 UID와 검증된 Google/Firebase ID 토큰 UID가 일치해야 하며 `auth_time`이 5분 이내여야 한다. 확인 문구 `회원 탈퇴`와 현재 정책 버전도 검사한다.

`accountDeletions/google-{uid}` 생성이 이용 중단 경계다. 계정별 트랜잭션, AI 결과 게시, Push 등록·일정 동기화·발송은 같은 문서를 확인한다. 기존 세션은 즉시 일반 API에서 거부된다. 소프트 삭제에서는 Firebase refresh token을 무효화하되 복구 로그인을 위해 Firebase 계정을 비활성화하거나 삭제하지 않는다. Google 계정 자체는 어느 단계에서도 삭제하지 않는다.

소프트 삭제 중 프로필·건강정보·읽기 모델은 원래 저장 범위에 남지만 서비스에서 조회·변경할 수 없다. 모든 기기의 Push 구독·일정·전송 상태는 해제한다. 복구는 건강정보를 다시 이용 가능하게 하며 이전 기기의 알림을 자동 재활성화하지 않는다.

탈퇴 계정의 Google 로그인은 일반 서비스 세션을 발급하지 않는다. 새 본인 확인 결과로 5분짜리 HttpOnly `ipillgood_account_recovery` 쿠키만 만들고 복구 화면으로 이동한다. 쿠키는 UID·해당 탈퇴 요청 ID·Google `auth_time`에 묶이며 건강정보 API나 탈퇴 처리 receipt 대신 사용할 수 없다.

복구 API는 현재 요청과 일치하는 새 Google 인증, 확인값, 만료일, 영구 삭제 미시작 상태를 검사한다. 복구와 영구 삭제 시작은 같은 문서의 트랜잭션을 사용하므로 동시에 성공할 수 없다. 이미 영구 삭제를 시작했거나 기한이 지난 계정은 복구하지 않는다. 재시도는 같은 요청에 한해 멱등 처리한다.

복구한 계정은 새 세션 버전으로 로그인한다. 탈퇴 전 발급한 다른 기기의 쿠키는 복구 후에도 유효해지지 않는다. 복구 상태의 계정별 메타데이터는 세션 차단 기준으로 유지하며 다시 탈퇴하면 새 요청 ID와 새 3개월 기한으로 교체한다. 로그인 토큰도 탈퇴 이전 `auth_time`이면 거부한다.

## 영구 삭제 범위

기한 후 영구 삭제는 `health-data-deletion.ts` 공통 함수로 처리한다. 기존 데모 정리도 이 함수를 사용하며 #55의 추후 건강정보 초기화 UI가 재사용할 수 있다.

- `careRecipients/{recipientId}` 및 동적으로 발견한 모든 하위 컬렉션. 부모 문서가 사라진 하위 데이터도 포함한다.
- `careReadModels/{recipientId}` 및 하위 데이터.
- 같은 recipientId의 `pushSubscriptions`, `medicationReminderSchedules`, `pushDeliveries`, `medicationReminderSync`. legacy sync 문서의 정확한 recipientId 키도 포함한다.
- Firebase Auth 사용자. Google 계정은 제외한다.

현재 계정과 돌봄 대상이 1:1인 모델을 전제로 한다. 이메일 또는 UID 접두사 검색으로 다른 계정을 삭제하지 않는다. 다중 보호자/소유권 이전(#82)은 구현하지 않았으며 해당 모델 도입 시 이 경계를 재검토해야 한다. 외부 AI 공급자의 로그·백업 등 앱의 Firestore 밖 데이터는 이 함수로 지울 수 없으므로 해당 범위와 처리 책임은 별도 검토가 필요하다.

영구 삭제 뒤 재가입은 새 UID의 빈 데이터 범위를 사용하며 이메일을 키로 이전 기록을 연결하지 않는다.

## 실패·동시 요청·재처리

동일 UID의 진행 중 요청은 한 작업으로 합쳐진다. 5분 작업 lease로 중복 실행을 제한하고 한 번에 최대 200개 문서를 지운 뒤 다음 요청/Cron에서 계속한다. 초기 알림·토큰 정리가 완료되면 `soft_deleted / waiting`으로 대기한다. 기한 전 Cron은 건강정보 삭제를 시작하지 않는다. 복구된 `restored` 계정은 삭제 작업 대상에서 제외한다.

소프트 삭제의 알림 대상 조회와 실제 삭제 commit은 분리한다. 실제 삭제 트랜잭션 안에서 해당 탈퇴 요청 ID, 작업 owner, `processing` 상태, 사용자 범위, 유효한 lease를 검사한 뒤 최대 200개를 삭제한다. 조회가 지연되거나 트랜잭션 도중 다른 작업이 계정을 복구하면 이전 작업의 삭제는 적용되지 않는다. 복구 후 새로 동의한 알림과 재탈퇴로 생성된 새 작업 상태도 보존한다. 진행 상태 checkpoint에도 같은 검사를 적용한다.

중간 실패는 `failed`로 남기며 완료로 표시하지 않는다. 서버가 죽어도 lease 만료 후 재처리한다. 초기 정리가 실패한 경우 복구 API에서도 재시도할 수 있으며 정리 완료 전에는 계정을 활성화하지 않는다. Auth 계정이 이미 없어진 경우에도 서비스 자격 증명으로 잔여 데이터를 지운다.

외부 AI·Push 작업은 사용자 범위 `processingLeases`에 등록한다. 탈퇴 접수 후 신규 작업은 거부하며 이미 승인된 작업이 끝나거나 장애 lease가 만료되기 전에는 소프트 삭제 정리나 영구 삭제를 완료하지 않는다. 기존 외부 호출 timeout보다 긴 5분 lease를 사용한다. 이미 Push 공급자에게 접수된 알림을 회수하는 기능은 없으며 그 알림은 공급자의 TTL에 따라 도착할 수 있다.

영구 삭제 시 Firebase 계정을 비활성화하고 데이터 정리 후 Auth 사용자도 삭제한다. 동일 데이터 범위를 다시 순회하고 Auth 사용자 부재를 확인해야 `completed`가 된다. 완료한 작업 기록은 Cron에서 제거하며 별도 8일 등의 보존 기간을 추가하지 않는다. 3개월 동안 일반 서비스 세션을 발급하지 않았으므로 최대 7일인 탈퇴 전 세션은 이 시점에 이미 만료됐다.

일반 세션을 제거한 뒤에도 별도의 서명된 HttpOnly `ipillgood_account_deletion` receipt로 해당 작업의 상태/재시도만 할 수 있다. 이 receipt로 계정을 복구할 수는 없다. 시작 응답이 유실되면 기존 서명된 세션으로 이미 접수된 본인 작업만 확인한다. 소프트 삭제 정리 완료 후 Firebase 브라우저 인증, PushSubscription, 표시 중인 알림, 앱 캐시와 앱 저장 키를 정리하고 로그인 화면으로 이동한다. 새 로그인은 이전 receipt를 제거한다.

## 운영 구성과 확인

서비스 계정에는 기존 Firestore 권한 외에 `firebaseauth.users.get`, `firebaseauth.users.update`, `firebaseauth.users.delete`가 필요하다. Cloudflare는 기존 `FIREBASE_SERVICE_ACCOUNT_JSON`, 로컬 Node는 ADC를 사용한다. 기존 Cron에 `/api/account/deletion/cleanup`을 연결했으며 `PUSH_CRON_SECRET`으로 보호한다. 정책 버전과 만료일은 접수 시 저장한다.

2026-08-28 사용자 요청으로 실제 Worker 계정에 세 권한만 가진 custom role `ipillgoodAccountLifecycle`을 연결했다. 누락된 Firestore 복합 인덱스 3개를 READY로 만들고 #99를 버전 `64773bb8-f2ff-4a5f-bd65-90e4196d2e9c`로 100% 배포했다. 실제 자격 증명의 Auth 조회·권한 검사·세 Firestore 쿼리, 운영 API 인증 경계, 프로필 안내·취소와 Cron 연속 2회 성공을 확인했다. Cloudflare는 실행 서버이며 사용자 계정·기록 저장소를 Firebase에서 옮긴 것이 아니다.

실제 Google 재인증 후 탈퇴 → 같은 Google 계정 로그인 → 복구와 모바일/PWA 실기기 복귀는 지정된 테스트 계정으로 별도 확인해야 한다. 로컬 자동 검증은 합성 계정과 Firestore/Auth 에뮬레이터만 사용한다. 개인/조직 계정의 탈퇴·삭제나 운영 3개월 기한 단축은 실행하지 않았으며 GitHub 이슈도 닫지 않았다.

## 검증

`npm run verify`는 임시 demo- 프로젝트, 로컬 Firestore/Auth 에뮬레이터, 외부 요청 차단 하에서 단위·타입·린트·빌드·저장소 계약·브라우저/API 검사를 수행한다. 실제 서비스 자격 증명을 사용하지 않는다.

2026-08-28 후속 풀사이클 검증에서 복구 후 새 알림을 지우는 지연 작업 경합 버그를 재현한 뒤 수정했다. 작업 소유권 검사와 알림 삭제를 같은 트랜잭션으로 묶고, 정확한 lease 만료·복구/재탈퇴 경합·200개 초과 분할 처리·Admin/REST 회귀 검사를 보강했다. scheduled 진입점 검사 5개를 추가한 최종 `npm run verify -- --account-full-cycle`은 **230개 통과·0개 실패**로 종료했다. 탈퇴 → 복구 취소 → 명시적 복구 → 재탈퇴 → 3개월 만료·영구 삭제 → 같은 Google 식별자로 재가입까지 확인했다. 후속 운영 조회에서 확인한 미배포·Auth 권한·인덱스 누락은 사용자 요청에 따라 모두 반영했고 실제 Cron 성공도 확인했다. 실제 Google 팝업 진입·취소와 운영 콜백 허용은 확인했으나 실제 계정 탈퇴·모바일 실기기 검증에는 테스트 계정 지정이 필요하다. [풀사이클 검증 보고서](account-deletion-verification.md)와 [운영 경계 검증 보고서](account-deletion-live-verification.md)를 확인한다.

검사는 재인증 만료·타 사용자·확인 누락·정책 버전 불일치, 월말·윤년·한국 시간 경계, 소프트 삭제 데이터 보존, Firebase 로그인 가능 상태, 명시적 복구·취소·기한 만료, 세션 버전 갱신, 복구와 삭제 경쟁, 재탈퇴 기한 갱신, 부분 삭제 실패, Auth 삭제 실패와 선행 삭제, 200개 초과 데이터, 중첩/고아 데이터, 다른 계정 보존, 진행 중 AI 결과 차단, Push 차단을 포함한다.

화면은 320/768/1024/1440px에서 탈퇴 안내와 복구 화면의 axe WCAG 검사, 키보드 확인·취소·포커스 복귀, 실패 재시도, 로그인 화면 복귀를 검사한다. 실제 Google OAuth·모바일 기기·운영 배포 검증을 대체하지 않는다. 실행 결과는 `verification-artifacts/verification.json`을 확인한다.
